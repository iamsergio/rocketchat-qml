# Architecture

A Rocket.Chat desktop client. The logic is in Rust and doesn't depend on any GUI. The first frontend is QML, connected to Rust through cxx-qt. A second frontend in Slint will come later and reuse everything below the GUI layer.

## Layers

```
┌───────────────────────────┐   ┌──────────────────────┐
│ QML (src/gui)             │   │ Slint (later)        │   views only, no logic
├───────────────────────────┤   ├──────────────────────┤
│ rc_qt  (cxx-qt bridge)    │   │ rc_slint (later)     │   view models, thread hop
├───────────────────────────┴───┴──────────────────────┤
│ rc_core  (application + domain)                      │   state, use cases, sync
├──────────────────────────────────────────────────────┤
│ rc_api   (Rocket.Chat protocol)                      │   REST + DDP, wire types
└──────────────────────────────────────────────────────┘
```

Dependencies only point downwards. Nothing in `rc_core` or `rc_api` knows about Qt or Slint.

- **rc_api**: a typed client for the Rocket.Chat REST API and the realtime DDP protocol over WebSocket. It keeps no application state. Wire (serde) types stay here, and `rc_core` maps them to domain types so that protocol quirks don't leak upwards.
- **rc_core**: domain types (rooms, messages, users, with ID newtypes), the session state machine, the sync engine and the use cases (log in, open a room, send...). Frontends drive it through a `Client` handle that accepts commands and emits events. It keeps lists such as the rooms in display order and the open room's messages (a `Timeline`, which merges history pages, de-duplicates and orders them) and emits index-based changes (insert, update, move, remove for rooms; reset, prepend, append, insert, update, move for messages), which view models apply one to one. It defines ports (traits) for what it needs from outside: the server API, secret storage, persistence (a `MessageStore` holds the messages loaded per room; in memory for now) and a file cache for downloads (`FileCache`). Adapters implement them, with in-memory versions for tests.
- **rc_qt**: cxx-qt QObjects and `QAbstractListModel`s that turn core events into Qt properties, signals and incremental model updates. It is the only crate that uses `unsafe` (cxx-qt bridge code).
- **QML**: presentation only. It binds to view models and calls their invokables. It has no business logic and makes no network calls.
- **C++ host** (`src/gui/main.cpp`): sets up logging through `rc_qt` (`rc_core::logging`: stderr, plus `<executable>.log` in developer-mode builds, filtered by `RUST_LOG`), creates `QGuiApplication`, starts the core (`rc_qt::start_core(cacheDir)`, with `QStandardPaths::CacheLocation`; `RC_SECRET_STORE` picks where the session is kept, see below), registers the Rust QML module, loads `Main.qml`, and, in builds with `ROCKETCHATQML_SPIX`, starts the Spix test server when given `--spix-port <port>`. In developer-mode builds, `--dev` fills in the login page for the local test server (`rc_qt::enable_dev_login()`; `RC_DEV_SERVER`, `RC_DEV_USER` and `RC_DEV_PASS` override it). Release builds compile neither the option (`#ifdef ROCKETCHATQML_DEVELOPER_MODE`) nor the Rust side (`developer-mode` feature). After the event loop ends it stops the core (`rc_qt::stop_core()`). It does nothing else.

`RC_SECRET_STORE` chooses the secret store at startup (`store_choice` in `crates/rc_qt/src/hub.rs`):

- unset, or any other value: the OS keyring, with memory as the fallback if there is none;
- `memory`: kept in memory only, forgotten at exit;
- `file:<path>`: a plain JSON file (`rc_core::adapters::FileStore`), so a GUI test can restart the app and resume. It writes the token in clear text, so it only exists in builds with the `test-file-store` cargo feature, which CMake turns on with `ROCKETCHATQML_SPIX`. Without the feature the value logs a warning and uses memory, never the keyring.

Adapter crates (added when needed): `rc_store_sqlite` (persistence) and a keyring-based secret store.

Test-only crates:

- **rc_gui_tests**: GUI tests that drive the running app through Spix's XML-RPC interface. They identify elements by path only, so the same tests can run against the Slint frontend. They run against the local test server.
- **rc_test_server**: blocking helpers that create users, rooms and messages on the local test server through its admin API (`Admin`, `unique()`), and `Proxy`, a TCP proxy in front of the server (std threads) that tests point the client at: `drop_connections()` cuts every open connection, and `set_accepting(false)` makes new ones close at once, so that a test can keep the client away for a while. The contract tests and the GUI tests share them. It may panic, since a failed call should fail the test.

There is no fake Rocket.Chat. Contract and GUI tests use the real local test server (`scripts/run_test_server.sh`), which CI shares. Failures it can't produce on demand are tested with port fakes in `rc_core`, wiremock in `rc_api` for REST, and for the DDP transport (silent servers, dropped connections, malformed frames) an in-process scripted WebSocket peer on an in-memory pipe, the WebSocket analogue of wiremock.

## Threading

- **GUI thread**: runs the Qt event loop and owns every QObject and model. Nothing on it blocks, and it never waits on the network.
- **Tokio runtime** (multi-threaded, few workers), owned by `rc_core`:
  - **Session actor**: a single task that owns the authoritative client state (session, room list, message store and the open room's timeline), so the state needs no mutexes. It processes commands one at a time. Each history fetch carries an attempt id, and its answer is dropped if the room was closed or another fetch began meanwhile.
  - **Store worker**: runs the secret-store calls (keyring or memory), which block and may wait for the user to unlock the keyring. It takes them in order, one at a time, on blocking threads, so a save and a later clear never swap and the async threads never stall.
  - **I/O tasks**: the DDP connection (read loop, ping), REST requests and avatar/file downloads. They report back to the actor through channels, tagged with the login attempt (or fetch) they belong to, and the actor drops what is stale. The sync engine is the actor plus one such task per connection, which opens the realtime connection (`ServerApi::realtime`, a receiver of pushed events that closes the connection when dropped) and forwards what it pushes. It works in cycles, one per connection: open the connection, fetch the rooms, and if a room is open fetch its newest page. The connection opens before the rooms are fetched, and what arrives until the list is set waits in a backlog and is replayed on top of it, so nothing between the snapshot and the subscription is lost. Subscription changes upsert or remove rooms; a pushed message joins the open room's timeline, and is ignored for any other room. A cycle ends when the connection ends or fails to open, or when its rooms fetch fails (an expired token ends the session instead): the actor drops the connection and starts a timer task that waits (`Backoff`: 1 s doubling to 60 s, cut randomly to between half and all of it, forgotten only when a cycle that opened the connection and listed the rooms then stayed connected for a minute, so a server that accepts and drops at once is not hammered), then starts the next cycle. The frontend is told with `Event::Connection` (`Waiting` with the wait, `Reconnecting` while a cycle tries, `Connected` once the rooms are listed again). `rc_qt` turns the latest one into the `Session.connectionText` property, which the banner of the room page shows. Reports and timers carry the cycle number, and logout, expiry and stopping abort the timer, so a stale one does nothing. Only the first listing of a session resets the room list; later ones are merged with `RoomList::sync` into inserts, updates, moves and removals, and a room that is gone is closed if it was open. The open room's newest page is merged by the timeline: it is appended if it touches the messages held, and replaces them if more than a page was missed.
- **Commands (GUI → core)**: sent on a non-blocking `mpsc` channel.
- **Events (core → GUI)**: the frontend gives `Client` an event callback, which the actor calls in order from a runtime thread. In `rc_qt` the callback belongs to a hub (`hub.rs`), the one owner of the `Client` in the process. It updates the hub's cache (the latest session state and a mirror of the room list and of the open room's messages) and hands each event to every registered view model through `CxxQtThread::queue`, where the view model applies it as a diff (insert, update, move or remove rows). A view model registers when it is created, on the GUI thread, and replays the cache under the same lock that queueing uses, so it misses nothing and applies nothing twice whenever QML creates it. Neither side waits for the other. Qt objects are never touched from a Tokio thread.
- **Shutdown**: dropping `Client` ends the actor, which first waits briefly (2 s at most) for a pending logout: the token revocation and the store clear. The GUI thread blocks for that bounded time only.

## Sending messages

`Client::send_message` picks the message's id itself (17 characters, like the server's), so that a retry can't post it twice and the server's echo can be matched to the local copy. The message goes into the room's messages at once as `Pending` (`Delivery`), in the open timeline or, if the room isn't open, in what the `MessageStore` holds of it, and `chat.sendMessage` runs in a task. The message becomes sent when the REST answer or the realtime echo arrives, whichever comes first, and the other finds nothing left to settle; it becomes `Failed` on any other error (an expired token ends the session instead). `retry_message` sends a failed message again under the same id. Switching rooms in between changes nothing: the answer is applied to the room it belongs to, shown or not.

The server stores a message once per id. Sending an id it holds already (the first attempt arrived, but its answer was lost) is refused with a 400 whose text is an internal error (`Cannot read properties of undefined (reading 'starred')`), which is nothing to recognise. `rc_api` therefore looks the message up by id after any 400 and, if it is in the same room and from the same user, takes it as the answer, so a caller may retry whenever it doesn't know whether an attempt arrived.

In the `Timeline` the messages the server confirmed come first, in display order, and the unsent ones after them in the order they were written: their time is the user's clock, which says nothing about where they fall among the server's. History pages, live messages and the catch-up after a reconnect therefore go in front of the unsent messages, which they never drop, and a page or a pushed message that carries the id of an unsent one settles it. Settling is an `Updated` change (same position) or, if the server's time puts the message elsewhere among the confirmed ones, a `Moved` one. The message list is never reset for it. A message confirmed while the room's newest page is still loading is also kept for that page, which may predate it.

## Rich text

A message's body is a `RichText` (`rc_core::rich`): `text`, what the author wrote (markdown source included, for previews, notifications and search), and `blocks`, what to show. `MessageKind::Text` holds it. Frontends render the blocks and know nothing of the server's wire format.

- **Blocks:** paragraph, heading (level 1 to 6), code (language, text), quote (holds blocks), bullet list, numbered list (first number, items), task list, big emoji (a message of nothing but emoji) and math. List items are inlines; the server doesn't nest lists, so an indented item comes out as text between two lists.
- **Inlines:** text, bold, italic, strike (they nest), code, link (URL and label, never empty), image, mention (`User`, `All`, `Here`), channel mention, emoji, math, color, timestamp and line break. An emoji has a shortcode, a Unicode character, or both: the server sends only the character for emoji typed as such, and only the shortcode for those typed by name (`:smile:`), so a frontend or a later lookup table turns shortcodes into characters or custom emoji. Whether a mention is of the user is for the frontend to say, by username.
- **Source:** the server's `md` tree, read by `rc_api::md` and mapped by `RichText::from_markdown`. Reading is lenient: a node type it doesn't know becomes its text (and is logged at debug), a malformed node is read as far as it goes, and none of it fails the message. The blank-line marker the server puts between blocks is dropped, since blocks stand apart anyway. Beware that Rocket.Chat's markdown differs from CommonMark: a single asterisk is bold, and `_x_` or `__x__` are italic.
- **Fallback:** a message without `md`, with one that isn't a list, or with one that shows nothing, is one paragraph of the text, with a line break inline for each newline. A message sent from here is such a message until the server's copy arrives.

**Showing it (rc_qt):** `rc_qt::rich_html` renders the blocks as the HTML subset of Qt rich text, in one pure function; QML only displays it (`msgBodyHtml`, `Text.RichText`, links open with `Qt.openUrlExternally`). All author text is escaped, and only `http`, `https` and `mailto` URLs become links. Highlights and code backgrounds are translucent so they read on light and dark themes; links take the palette's `linkColor`. Math is its TeX source in monospace, and markdown images are links. Qt can't draw a bar beside a multi-line quote, so the bar covers only its first line. `msgBody` keeps the text as written, which is what the GUI tests compare; `msgBodyHtml` holds the HTML.

- **Mentions:** `RichText::mentions` and `Message::mentions` (rc_core) say whether a message calls a username, `@all` or `@here`. The `MessageList` model knows the logged-in username through the hub's cache and exposes `mentionsMe` (not for one's own messages), which the delegate uses to tint the row (`msgMentionsMe`). The mentions of the user, `@all` and `@here` are drawn stronger than others.
- **Emoji:** `rc_core::emoji` maps shortcodes to Unicode (the `emojis` crate, gemoji names) and the server's custom emoji to image URLs. The core lists them with `emoji-custom.list` after the rooms of each sync cycle and sends `Event::CustomEmoji` when they change; custom ones show as an `<img>` of fixed size, unknown shortcodes stay as `:name:`. The model re-renders its rows when the user or the emoji change.

## Avatars

Avatars are files in a cache directory, which the GUI loads by `file://` URL. The core fetches them, so QML makes no network calls.

- **Port:** `FileCache` (`rc_core::ports`) maps a `CacheKey` (server, kind, name) to a file: `get` finds it, `put` stores bytes in the type the media type says (svg, png, jpg, gif or webp) and says whether the content changed. The server in a key is its host and port (and path prefix), so each server has its own files; the kind is `avatars/user/<username>`, `avatars/room/<room id>` or `attachments` (named by the file's path on the server, see Attachments). `DiskFileCache` keeps `<root>/<server>/<kind>/<name>.<ext>`: every part is escaped to one safe file name (letters, digits and `_-.` stay, every other byte, and a leading dot, becomes `%XX`, so a username can't leave its directory and two names never share a file), and `put` writes a temporary file in the same directory and renames it, so a reader never sees half a file. A copy of another type is removed after the new one is in place. The root is `QStandardPaths::CacheLocation`, which the C++ host gives `start_core`. Logging out keeps the files; nothing is evicted yet (PLAN.md, Phase 6).
- **Whose avatar, and whether there is one:** a user's (`/avatar/<username>`) or a room's (`/avatar/room/<id>`). The server answers every name with an avatar it draws (initials on a colour, an SVG; for a room from its id, so a channel gets the first character of its id), so only an avatar somebody uploaded is worth showing. What tells is `avatarETag`: `rooms.get`, which the room list reads anyway, has it for the rooms that have one, and `users.info` and `rooms.info` have it for a user or a room. It is absent for the drawn ones, and appears a moment after an upload; a real SVG avatar is no casualty, as the media type isn't looked at. A direct message has no avatar of its own, so the room shows the other user's. The actor wants the avatars of the rooms with an etag and of the other users of direct messages, whenever the list is set or a room joins it, and of the authors of the open room's messages (system messages have none), whenever the timeline changes. The download of a user's or room's avatar asks `users.info` or `rooms.info` first and fetches nothing for a user or room that has none. Everybody else shows initials.
- **Refresh policy:** the first time an avatar is wanted in a session, a cached file is sent at once (`Event::Avatars`: owner and path) and the avatar is downloaded again in the background, once per session. The new file is sent only if its content differs from the cached one. Downloads are deduplicated (an owner is looked at once) and at most four run at once, off the actor, tagged with the login attempt; the answer of another attempt is dropped. When the server says there is no avatar of its own, a cached file is deleted and, if it was sent, the frontend is told it is gone (an avatar that was removed, or a file kept from before this was known). A refused avatar, or a type the cache doesn't keep, means no avatar and is logged only: `Unauthorized` doesn't end the session either, since the avatar route isn't under `/api/v1` and the rooms and messages meet the same refusal if the token is dead. A download that failed for lack of a connection is wanted again at the next sync cycle. No conditional request is made: the server sends neither `ETag` nor `Last-Modified` with the image, and the content is compared. The etag of the user or room is only asked, not kept. The server pushes avatar changes of everybody on `stream-notify-logged` (`updateAvatar`, by username or room id), and the connection subscribes: one for an avatar that is shown, or for a room of the list (it may have had none), is looked at again. Logging out sends the frontend an update that forgets every avatar.
- **Qt side:** the hub keeps the avatars as URLs, `file://<path>?v=<n>` with `n` growing each time a file is announced (QML caches images by URL, so a replaced file needs a new one). `MessageListModel` and `RoomListModel` have `avatar`, `avatarInitials` and `avatarColor` roles; when avatars arrive only the rows that use them get a `dataChanged` for `avatar`, in runs of consecutive rows. The `Avatar` component draws the image rounded, or the initials on a colour until it has loaded, which is for good when there is no avatar: the initials are those of the display name (of a room's name, and for a direct message the other user's), the colour comes from the username (the room's name). The rounding is a mask effect, which the software scene graph doesn't draw: there (the offscreen platform, so the GUI tests) the corners stay square.
- **Not tested end to end:** the image of a custom avatar. `users.setAvatar` and a room's `roomAvatar` (`rooms.saveRoomSettings`) are accepted and announced on the stream, and the etag shows, but the test server keeps serving the drawn avatar from `/avatar/...`. So the tests check that a user or room with an etag gets a file in the cache and a loaded `Avatar`, not what the picture is; the replaced-file path is covered by unit tests and a mock HTTP server.

## Attachments

A message carries its file attachments (`rc_api::Attachment`, `domain::Attachment`): title, the path of the original, description, size, and for an image the path of the picture and its dimensions in pixels. Other kinds of attachment (quotes, integrations) are not read, and a malformed entry is skipped without failing the message. The picture of a big image is a thumbnail the server made; the original stays behind `link`.

- **Download:** the files are under `/file-upload/`, which answers 403 without the login headers, so QML can't load them. `RestSession::file` takes the server path of a message, refuses anything that doesn't start with `/file-upload/` (a full URL, another place on the server, `..`, a query), so the login headers can't go anywhere else, and decodes each segment before the request escapes it again.
- **Cache:** `images.rs` is `avatars.rs` without the refresh. An uploaded file never changes, so when messages enter the timeline (the same places that want the authors' avatars) the actor looks each image up in the cache by `CacheKey::attachment` (server, path): a file that is there goes to the frontend at once (`Event::Images`: path and file) and is never downloaded, any other is downloaded once per session, at most four at a time, off the actor and tagged with the login attempt. A type the cache doesn't keep, or a refusal, means no image and is only logged; a download that failed for lack of a connection is wanted again when the image next comes up. Logging out sends an update that forgets every image; the files stay.
- **Qt side:** the hub keeps the files as URLs like the avatars (`ImageUrls`, `file://<path>?v=<n>`). The `MessageList` model has an `attachments` role, a list of maps (`title`, `description`, `size` in words, `link`, `isImage`, `image`, `width`, `height`), made by `attachment_view`. `link` is the server's address (the `Viewer` knows it) plus the path; `image` is the local file URL, empty until the download is done, when only the rows of messages that show that image get a `dataChanged` for the role. The delegate draws an image inline at its size (at most 360 wide), under a grey box until it loads, and a file as a link with its size. Both open `link` with `Qt.openUrlExternally`, without the token: it works when the browser has a Rocket.Chat session. Downloading through the app comes with file upload (PLAN.md, Phase 5).

## GUI testing contract

There is one GUI test suite, `rc_gui_tests`, and it runs unchanged against both frontends. It is a Spix XML-RPC client and never links to either GUI. Each frontend embeds a server that speaks the same protocol:

- **QML frontend:** C++ Spix (`Spix::QtQuick`), started by the C++ host.
- **Slint frontend:** a Rust implementation of the Spix RPC server built on Slint's Rust testing API (`ElementHandle`, `query_descendants()`). The C++ `Spix::Slint` backend can't be used there: it needs C++-generated Slint components, and a Rust Slint app has a different Slint runtime.

Paths are kept shallow and decoupled from layout: `<window>/<name>`, where `name` is unique per window (for example `mainWindow/loginServerField`). A list row is addressed by its room id, not by its text (Spix's `"text"` selector), because room names aren't unique: the row's name is `room_<id>` and its parts (`roomName`, `roomKind_<kind>` (an icon, named after the room kind: `channel`, `private` or `direct`), `roomAvatar` (visible once the avatar image has loaded; its `text` is the `file://` URL), `roomAvatarPlaceholder` (the initials, visible until then), `roomUnread`, `roomMentions`) sit below it, as in `mainWindow/room_<id>/roomUnread`. A message row is `msg_<message id>` the same way, with `msgAuthor`, `msgAvatar` and `msgAvatarPlaceholder` (as for rooms), `msgTime`, `msgBody` (its `text` is the message as written), `msgBodyHtml` (its `text` is what is shown, as HTML), `msgMentionsMe` (visible if the message mentions the user) (or `msgSystem` for a system message, which has no author or body) and `msgDaySeparator` when the message starts a day, as in `mainWindow/msg_<id>/msgBody`; the files of a message are `attachment<N>` below it (N from 0), with `attachmentImage` (visible once the picture has loaded; its `text` is the `file://` URL), `attachmentPlaceholder` (until then), `attachmentLink` for a file that isn't an image (its `text` is the address it opens) with `attachmentTitle` and `attachmentSize` in it, and `attachmentDescription`, as in `mainWindow/msg_<id>/attachment0/attachmentImage`; `msgBody` is hidden for a message of only files; an unsent message also has `msgPending`, or `msgFailed` and `msgRetry`, which exist only in that state, so that a test, which can't know the id the client picked, finds the one unsent message by name alone (`mainWindow/msgFailed`); the composer is `composerField` (Enter sends, Shift+Enter starts a line) and `composerSend`; the list is `messageList` (its `count` is the loaded messages, not those in view), with `historyStart` above the first message once nothing older exists. The tests scroll with Home, since Spix has no wheel. Spix searches depth-first, so the path doesn't have to name the `ListView` or the delegate's other ancestors; it finds only rows that exist, and a `ListView` creates the delegates in view, so a test of a list longer than the window has to scroll first. In QML the name is the `objectName`; in Slint it is the `accessible-id`. The path constants live in `rc_gui_tests`, which is the single source of truth.

Tests use only the part of the Spix protocol that both servers implement: clicks, key and text input, `existsAndVisible`, get/set of `text`, `checked`, `enabled`, `count` and geometry, `wait` and `quit`, plus `getErrors`, which the `Gui` client checks after every call so that a wrong path fails the test. The core works asynchronously, so tests never sleep: `Gui::wait_until` and its `wait_until_visible`, `wait_until_hidden` and `wait_until_text` poll with a timeout and name what they were waiting for. `App::quit_and_wait` calls `quit` and waits for the app to exit by itself, so that it stops its core (a pending logout or store write finishes) before a test starts it again.

The harness starts the binary named by `RC_GUI_TEST_APP` with `--spix-port <free port>`, `QT_QPA_PLATFORM=offscreen`, `XDG_CACHE_HOME` set to a directory of its own (empty at launch, removed with the app: `App::cache_dir`, so a test can look at the avatar files) and `RC_SECRET_STORE=memory` (the app starts the core at launch, and its default secret store is the OS keyring, which on a developer machine is the user's real wallet). A test can override these with `App::launch_with`, for example with `RC_SECRET_STORE=file:<path>` to keep the session between two runs. The GUI tests are `#[ignore]`d, so a plain `cargo test` skips them (it runs before the app is built in CI) and never reports them as passed. ctest runs them with `--ignored` and `RC_GUI_TEST_APP` set; without it they fail. The tests that log in create their own users and rooms on the test server through `rc_test_server`, so they also need `RC_TEST_SERVER_URL`.
