# Avatars

Avatars are files in a cache directory, which the GUI loads by `file://` URL. The core fetches them, so QML makes no network calls.

- **Port:** `FileCache` (`rc_core::ports`) maps a `CacheKey` (server, kind, name) to a file: `get` finds it, `put` stores bytes in the type the media type says (svg, png, jpg, gif or webp) and says whether the content changed. The server in a key is its host and port (and path prefix), so each server has its own files; the kind is `avatars/user/<username>`, `avatars/room/<room id>` or `attachments` (named by the file's path on the server, see [Attachments](attachments.md)). `DiskFileCache` keeps `<root>/<server>/<kind>/<name>.<ext>`: every part is escaped to one safe file name (letters, digits and `_-.` stay, every other byte, and a leading dot, becomes `%XX`, so a username can't leave its directory and two names never share a file), and `put` writes a temporary file in the same directory and renames it, so a reader never sees half a file. A copy of another type is removed after the new one is in place. The root is `QStandardPaths::CacheLocation`, which the C++ host gives `start_core`. Logging out keeps the files; nothing is evicted yet ([PLAN.md](../../PLAN.md), Phase 6).
- **Whose avatar, and whether there is one:** a user's (`/avatar/<username>`) or a room's (`/avatar/room/<id>`). The server answers every name with an avatar it draws (initials on a colour, an SVG; for a room from its id, so a channel gets the first character of its id), so only an avatar somebody uploaded is worth showing. What tells is `avatarETag`: `rooms.get`, which the room list reads anyway, has it for the rooms that have one, and `users.info` and `rooms.info` have it for a user or a room. It is absent for the drawn ones, and appears a moment after an upload; a real SVG avatar is no casualty, as the media type isn't looked at. The avatar routes read the login from the cookies (`rc_uid`, `rc_token`), not from the `X-User-Id` and `X-Auth-Token` headers, and without them draw the avatar even for an uploaded one, so the download sends both. A direct message has no avatar of its own, so the room shows the other user's. The actor wants the avatars of the rooms with an etag and of the other users of direct messages, whenever the list is set or a room joins it, and of the authors of the open room's messages (system messages have none), whenever the timeline changes. The download of a user's or room's avatar asks `users.info` or `rooms.info` first and fetches nothing for a user or room that has none. Everybody else shows initials.
- **Refresh policy:** the first time an avatar is wanted in a session, a cached file is sent at once (`Event::Avatars`: owner and path) and the avatar is downloaded again in the background, once per session. The new file is sent only if its content differs from the cached one. Downloads are deduplicated (an owner is looked at once) and at most four run at once, off the actor, tagged with the login attempt; the answer of another attempt is dropped. When the server says there is no avatar of its own, a cached file is deleted and, if it was sent, the frontend is told it is gone (an avatar that was removed, or a file kept from before this was known). A refused avatar, or a type the cache doesn't keep, means no avatar and is logged only: `Unauthorized` doesn't end the session either, since the avatar route isn't under `/api/v1` and the rooms and messages meet the same refusal if the token is dead. A download that failed for lack of a connection is wanted again at the next sync cycle. No conditional request is made: the server sends neither `ETag` nor `Last-Modified` with the image, and the content is compared. The etag of the user or room is only asked, not kept. The server pushes avatar changes of everybody on `stream-notify-logged` (`updateAvatar`, by username or room id), and the connection subscribes: one for an avatar that is shown, or for a room of the list (it may have had none), is looked at again. Logging out sends the frontend an update that forgets every avatar.
- **Qt side:** the hub keeps the avatars as URLs, `file://<path>?v=<n>` with `n` growing each time a file is announced (QML caches images by URL, so a replaced file needs a new one). `MessageListModel` and `RoomListModel` have `avatar`, `avatarInitials` and `avatarColor` roles; when avatars arrive only the rows that use them get a `dataChanged` for `avatar`, in runs of consecutive rows. The `Avatar` component draws the image rounded, or the initials on a colour until it has loaded, which is for good when there is no avatar: the initials are those of the display name (of a room's name, and for a direct message the other user's), the colour comes from the username (the room's name). The rounding is a mask effect, which the software scene graph doesn't draw: there (the offscreen platform, so the GUI tests) the corners stay square.
- **Tested end to end:** `users.setAvatar` and a room's `roomAvatar` (`rooms.saveRoomSettings`) upload a one-pixel PNG, the etag shows, and the contract tests check that the download is that `image/png` (the cached file is a `.png`); the drawn avatars stay `image/svg+xml`. The replaced-file path is covered by unit tests and a mock HTTP server.
