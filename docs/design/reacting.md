# Reacting to messages

`Client::react(id, emoji, react)` adds the user's reaction to a message of the open room, or takes it back. The emoji is a shortcode, with or without colons, and goes out as `:name:`. Any author will do: the rule (`policy::can_react`) is that the message is sent and says something (not a system message). Unlike an edit or a deletion it asks nothing of the server's settings; a reaction the server refuses (an emoji it doesn't know) is shown as its refusal.

- **Request:** `POST /api/v1/chat.react` with `messageId`, `emoji` and `shouldReact`. The request always says which of the two is wanted and never leaves it to the server's toggle, so a repeated request, or one made twice by a retry, changes nothing. The server answers a repeated reaction with a success and leaves one user in the list. It refuses an emoji it doesn't have.
- **Answer:** as for edits and deletions, one `Event::MessageAction` (`React`, and `Ok` or an `ActionError`). A message the rule doesn't allow, one that is not in the open room, and a blank emoji are refused at once, without a request; "This message can't be reacted to". Ignored when logged out. An answer after a logout is dropped, and a dead token ends the session.
- **Applying it at once:** on success the core puts the user's username in the held message's reaction, or takes it out (`Message::set_reaction`), without waiting for the push. A reaction that is new goes at the end of the list, as the server does, and one left without users goes. The users of a reaction are a set, so the push that comes before or after the answer, which carries the same reaction, changes nothing. The change is made to the message as it is when the answer arrives, not as it was when the reaction was asked for, so a reaction of somebody else that was pushed meanwhile is kept. It reaches the frontend as `Timeline::replace` does: an `Updated` change, no reset. A page that was asked for before the reaction may predate it, so the changed copy joins it, as for an edit. The message is not touched if it has gone meanwhile.
- **The order of the reactions:** the server lists them in the order they were first made. The copy pushed over DDP goes through `serde_json::Value`, which keeps the order only with the `preserve_order` feature, so that is on: without it a pushed message listed its reactions alphabetically and the chips jumped.

## The emoji picker

Rocket.Chat names and validates reactions with the `emojione` npm package (4.5.0, the latest release, which its web client uses too), not with gemoji, which the `emojis` crate knows. Probing the test server with every gemoji shortcode, 662 of 1870 were refused ("Invalid emoji", for example `melting_face`, `hugs`, `roll_eyes`), and where both are accepted the server stores the reaction under the name it was sent, so `:+1:` and `:thumbsup:` would be two chips for the same emoji. The client therefore sends emojione's canonical names (the server accepted all 1672 of them, skin tones excluded).

- **The table:** `crates/rc_core/data/emojione.tsv`, one line for each entry of the package's `emojioneList`, skin tones included, which are needed to show a reaction: the canonical shortcode, the glyph, the alternate shortcodes (comma-separated) and the category. It is generated by `scripts/update_emojione.py`, which downloads the pinned version; run it to move to another one. Only the package's non-artwork files are used, which are MIT (the data file is annotated in `REUSE.toml`). The core reads it once (`include_str!`, `LazyLock`).
- **The catalog:** `rc_core::emoji::catalog` lists what a picker offers: the server's custom emoji first, by name, then the standard ones in the order of the `emojis` crate, base forms only. A standard emoji is there only if emojione has the same glyph (ignoring U+FE0F), under emojione's canonical name as its shortcode. The hair components, skin tones, modifiers and regional indicators are left out. Each `PickerEmoji` has the shortcode between colons, the Unicode text (empty for a custom emoji) and the image URL (empty for a standard one). `emoji::search` keeps the ones with any name that contains the query, ignoring case: the canonical name, the alternates and gemoji's, so `+1`, `thumbsup` and `thumbup` find the thumbs-up, and `hugs` and `hugging` the hugging face. A blank query keeps all of them. A contract test reacts with every shortcode of the catalog and fails on any the server refuses.
- **Showing names:** `emoji::unicode` looks gemoji's name up first, then emojione's (canonical or alternate, tones included), so a reaction or a `:name:` that another client sent shows as a glyph when only emojione knows the name.

## Qt side

- **`EmojiCatalog`:** a list model (`emoji_picker_model.rs`), a QML singleton like the other models. Its roles are `shortcode`, `glyph` and `image`; its `query` property filters, in Rust (`emoji_picker_view::Picker`), by resetting the model: a filter changes the whole list, so there is nothing incremental to say. It registers with the hub, which gives it the custom emoji the cache holds and queues the new list when the core sends `Event::CustomEmoji`; it keeps the query. There is one picker, so a singleton does. An element created by QML would not do for qmllint: it can't resolve `QAbstractListModel` as a type.
- **`query` has a custom setter:** `WRITE = set_query_text`, an invokable of the model (cxx-qt writes no setter that runs our code).
- **`MessageList`:** a `canReact` role, from `policy::can_react`. **`Room`:** `react(messageId, emoji, reacted)`; a failure is in `actionError`, the room page's dismissable error bar, as for edits.
- **QML:** a chip toggles the user's own reaction (`mine` takes it back, else it adds that emoji) when the message can be reacted to. The message menu has "Add reaction" (`msgReactAction`), and a message that has reactions ends its row of chips with a "+" (`reactionAdd`); both ask the room page to open `EmojiPicker.qml`, a popup with a search box (`emojiSearch`, focused when it opens, empty each time) and a grid (`emojiGrid`) of the emoji that match. Each is named `emojiPick_<shortcode without colons>`, shows its shortcode as a tooltip, and a click reacts with it and closes the popup, as Escape does.
- **Spix:** the picker is a popup, so its items are addressed from the window (`mainWindow/emojiSearch`) and exist only while it is open, and the grid creates only the emoji in view: a test searches for the one it wants before clicking it. The chips and the picker's emoji use a `MouseArea`, since `TapHandler` didn't react to Spix clicks (see [Editing and deleting your own messages](editing-own-messages.md)).

## Slint side

- **Chips:** `msgReactions` is a `FlexboxLayout` (Slint 1.18 wraps; no hand-made flow) of `reaction<index>` pills, with the same names, sizes (`chip-height`, `chip-padding`, `chip-emoji-size` in `theme.slint`) and colours as the Qt chips. The row's `reactions` is a `[ReactionRow]` (`emoji`, `label`, `text`, `has-image`, `image`, `count`, `mine`) made by `rows.rs` from `reaction_view::reactions`, only for a message that has reactions. `label` is what `reactionEmoji` exposes to the tests (glyph, else the server's image URL, else the shortcode); `text` is what is drawn when there is no image (the glyph, or the shortcode while a custom emoji has no file yet). The row has `can-react` from `policy::can_react`; a click on a chip calls `react(id, shortcode, !mine)` through the account only when it holds, and the answer is `Event::MessageAction`, whose failure goes to the room action error.
- **Custom emoji files:** `MessageList` holds the `EmojiImageUrls` of the cache. `MessageModel::show` and `apply` return the custom emoji names of the messages they were given (the snapshot, or the messages in the changes), and `app.rs` asks the account for them with one `want_emoji_images`; the core dedupes. `Event::CustomEmoji` sets the viewer (which knows the emoji now) and asks for the names of all rows, since the core ignored names the server's list didn't hold. `Event::EmojiImages` refreshes only the rows whose message reacts with a changed emoji (`MessageList::set_emoji_images`, runs of rows like avatars).
- **Menu, double-click and "+":** `MessageMenu` has `can-react` (`policy::can_react`, asked when the menu opens), `has-menu` includes it, and "Add reaction" sits between Quote and Edit. `reactionAdd` is the last child of the chips' `FlexboxLayout`, shown when the message can be reacted to (so only where there are chips); it keeps its place and fades in with the pointer over the message (`row-touch` or a chip, which takes the pointer from the row behind it). A double-click is the `double-clicked` of the row's `TouchArea`. Slint's `StyledText` accepts every mouse event, not just those on a link, so the row behind never sees a click on the text: a body without links (`MessageRow.has-links`, from the rendered HTML) gets a `TouchArea` over its text for the double-click, and one with links only reacts beside the text. All three call `add-reaction(id)`, up to `MainWindow`, which remembers the id in `picking-id` and tells Rust.
- **The picker:** `EmojiPicker` is a dimmed overlay like `ConfirmDialog` (Escape and a click outside cancel; the panel takes its own clicks) with an `InputField` (`emojiSearch`, focused in `init`, new at each opening so empty) and a `ListView` of rows. Slint has no grid and there are about 1900 emoji, so `EmojiPickerModel` is a `Model` of rows, each a `ModelRc<EmojiCell>` of `emoji-columns` cells (the picker's width less its padding over `emoji-cell-size`, a constant of `MainWindow` that Rust reads at start) made when the list asks for the row. Only rows in sight have cells, so `emojiPick_<name>` exists only for those; the tests search first. The model wraps one `rc_view` `Picker`; `emoji-query` sets the query (a reset), `Event::CustomEmoji` and an account switch (`show_all`) give it the account's custom emoji (a reset; the catalogue is rebuilt, ~2000 entries). Opening asks `want_emoji_images` for all custom names (the core dedupes), and so does `Event::CustomEmoji` while it is open. `Event::EmojiImages` notifies only the rows that hold a changed custom emoji, which come first in the catalogue, so finding them walks the custom emoji and no more. A pick calls `react(id, shortcode, true)` and closes; a failure shows in the room action error.
