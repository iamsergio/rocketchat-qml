# Directory

The room list's search field (ROOM-010, [Search](room-list.md#search)) finds the user's own rooms locally and at once. The server's directory adds to it: the people the user has no direct message with, and the public channels the user is not in. Opening a person starts a direct message (ACT-007); opening a channel previews it, and the user may join (ACT-008). This is the core and `rc_view` part, the [Qt side](#qt-side) and the [Slint side](#slint-side).

## What the server does

The contract tests (`crates/rc_api/tests/contract.rs`, `crates/rc_core/tests/contract.rs`) record it. Checked on Rocket.Chat 8.0.

- **Directory:** `GET /api/v1/directory?text=<t>&type=users|channels&workspace=local&count=N&offset=0`, with `sort={"usersCount":-1}` for channels. `text` and `type` are parameters of their own: the older `query={"text":..,"type":..}` is ignored on Rocket.Chat 8 and the server then lists every room (70,219 on the test server). The answer holds the entries as `result`, and `total`. A user has `_id`, `username`, `name`, `createdAt` and `emails`, which `rc_api` drops. A channel has `_id`, `name`, `fname` (only if it differs), `t`, `usersCount`, `ts`, `default`, `lastMessage` and a `topic` if it has one; it has no `avatarETag`. Only public channels are listed, never a private group. The directory does not say whether the user is in a channel.
- **Direct message:** `POST /api/v1/im.create {"username"}` answers `{"room":{"_id","rid","t":"d","usernames"}}`. It is idempotent: the same room the second time, and a direct message the user had closed is opened again (`subscriptions.getOne` has `open: true` after). **It does not check the username**: an unknown one makes an empty direct message with a name nobody has. So the core only asks for usernames the directory gave.
- **Joining:** `POST /api/v1/channels.join {"roomId"}` answers `{"channel":{..}}`, and succeeds for a channel the user is in. A private group or a room that doesn't exist is a `Server` error. The join adds a system message to the channel and a subscription with one unread message and a mention. The server pushes the subscription.
- **One subscription:** `GET /api/v1/subscriptions.getOne?roomId=` answers `{"subscription": null}` for a room the user is not in. The subscription lacks the time of the last message, the avatar's etag and the topic, which `rooms.info` has, so `RestSession::subscription` asks both, as `subscriptions` does with `rooms.get`.
- **Looking without being in:** a user who is not in a public channel (permission `preview-c-room`, granted to `user`) can read `rooms.info`, `channels.history` and `chat.syncMessages` of it. A private group is refused.
- **Live updates without being in:** all three arrive for a user who is not in the channel, on the streams the core has open already. The messages come on `stream-room-messages` with `__my_messages__`, which carries the messages of every public channel (not those of private groups), and also the join messages of everybody in `GENERAL`. The deletions (`<room>/deleteMessage`) and the typing (`<room>/user-activity`), which the core follows for the open room, are accepted for such a channel. So a preview needs nothing new on the connection: no subscription to the room, no polling.

## Searching

`AccountHandle::search_directory(text)` is called on every change of the field's text. The core:

- trims the text; an empty one cancels the pause and the request and clears the results;
- tells the frontend at once with `Event::Directory` (the query, state `Searching`, no results), and waits for the typing to stop (300 ms; `Tuning::directory_debounce`, `RC_DIRECTORY_DEBOUNCE_MS` in whole milliseconds, `0` for no wait: a testing aid) before it asks. The wait is a deadline of the actor (`next_deadline`), not a timer task, so it runs on the fake clock in tests;
- then asks the users and the channels in parallel, 10 of each (`RESULTS_PER_KIND`: a frontend shows 5 of each, and the user's own rooms among the answers are filtered out of the 10), in one task;
- a newer text, or a clear, ends the request in flight and the answer of a request that was ended is dropped by its attempt id; so is the answer after a logout;
- answers with `Event::Directory` in state `Ready`, with the people, the channels and the server's totals, or `Failed` with a text (`DirectoryError`: "Can't reach the server's directory", or the server's message). An expired token expires the session, as everywhere;
- wants the avatars of the people (`AvatarOwner::User`) and of the channels (`AvatarOwner::Room`), like the room list's: the download asks the server whether there is one, and the 20 rows are cheap;
- the same text again does nothing, whatever the state, except after a `Failed`: then it asks again at once, without the wait. That is the **Retry**: the frontend calls `search_directory` with the field's text again.

A logout clears the search (an `Event::Directory` with the empty query, if it held anything).

## What is shown

`rc_view::directory::directory_view(result, listed, quiet, own_username)` (and `Cache::directory_view()`, over the account's cache) is a plain function, so both frontends show the same. The core's result is the server's, whole. The view leaves out the user and the people with a direct message with them (a quiet one too: its `peer` is the other user's username; usernames compare without regard to case), and the channels whose id is one of the account's rooms, the quiet ones included, then keeps 5 of each. `people_more` and `channels_more` count what the server has beyond what it sent, plus what the cut dropped: "N more, keep typing". They are an upper bound, since some of the entries beyond may be rooms the user has. The view is recomputed whenever the room list changes (`Event::Rooms`, `Event::QuietRooms`), with no new search, so a channel just joined or a direct message just opened drops out.

`Cache` keeps the last `Directory` (`directory()`), the last `DirectoryAction` and its state (`directory_action()`) and the previewed room (`preview()`), reset to nothing when the session ends. The switchboard routes the new events like the others.

## Actions

Each is a command of `AccountHandle` and answers with `Event::DirectoryAction { action, state }`: `Working` when it starts, then `Done`, or `Failed(RoomActionError)`, whose text is meant to be shown as it is, in the room list's error strip, as the room menu's. The busy look ("Opening…", "Joining…") is `Working` for that action in `Cache::directory_action()`. One runs at a time; a command that comes while another is under way is ignored (logged at debug), so the frontend keeps the row busy and the others inert. The answer of an action whose session ended is dropped (attempt id); nothing comes then, and the cache forgets the action. An expired token expires the session. All three are ignored unless logged in.

- **`open_direct(username)`** (`DirectoryAction::OpenDirect`): `im.create`, then `subscriptions.getOne` and `rooms.info` for the room, which goes into the room list (`upsert_now`) without waiting for the realtime push, and then the room is opened like any (`open_room`). The push, before or after, changes nothing: the room is the same. A direct message that went quiet (ROOM-008) comes back as the open room, as when it is opened from the search. Order: `Rooms` (the insert, if new), the events of opening the room, `Done`.
- **`preview_channel(room_id)`** (`DirectoryAction::Preview`): a channel the room list has is just `open_room`. Else `rooms.info` builds a `Room` (a public channel only; anything else is a failure), and the channel opens as the open room though the room list lacks it. `Event::Preview(Some(room))` comes first, for the header, then the events of opening the room, then `Done`. Nothing is marked read (it has no subscription), it is not in `Rooms`, `Unread` or `QuietRooms`, and a frontend keeps it out of the room search. Everything of an open room works: history, live messages, deletions, typing, and the catch-up after a reconnect (a preview is not closed for lacking a subscription). Sending is refused, as for any room the list lacks. The preview ends, with `Event::Preview(None)`, when another room is opened (the user stays out of the channel), the room is closed or the session ends, and when the room list has the channel (after the `Rooms` event that lists it, so also when the user joined from another client). A preview still on its way when another room is opened is cancelled (`Done`).
- **`join_channel(room_id)`** (`DirectoryAction::Join`): `channels.join`, then the subscription as above goes into the room list. If the channel is the preview, it stays the open room: the timeline is not reset (no `Timeline` event comes), the room is read as any open room, and `Preview(None)` comes after the `Rooms` event that lists it. Ignored for a channel the list has. A failure leaves the preview as it was.

## Qt side

Everything is in the room list's search ([Search](room-list.md#search)): its field, Ctrl+K, the results laid out from the field up, the cursor, Enter, Escape, the error strip `roomListError`.

- **Rows:** `rc_view::directory::search_rows(query, rooms, directory, view)` makes the results as one list, top to bottom as on screen: a label and the channels, a label and the people, then the user's rooms; each group has its best match at the bottom, nearest the field, and a group with more than it shows ends (below its rows) with a "N more, keep typing" line (`SearchRow::More`). The label over the user's rooms ("Your rooms") shows only when the directory has something above them or is not done, so with no directory results the rooms look as they did before. Between the people and that label sits a row that says the directory is being searched (`Searching`), or could not be (`Failed`, with the text of `failed_text` and a Retry); the user's rooms never leave for it. A directory that holds another query than the one typed (the core's first event of the search has not come) counts as searching and its results are not shown, so a frontend never flashes the last search's people. `SearchRow::actionable` says which rows the cursor can be on (rooms, people, channels), `first_actionable` and `next_actionable` move it, and `is_busy_with` says whether the action under way is about a row.
- **Model:** `RoomSearch` (`room_search_model.rs`) is that list, kept bottom to top (row 0 is right above the field), with a `rowType` role (`room`, `label`, `searching`, `failed`, `person`, `channel`, `more`) and the room roles for a room, `name`, `roomId` (a channel's), the avatar roles, `username`, `members`, `busy`, `group`, `count` and `text` for the others; every row answers the roles its delegate reads, with nothing if they mean nothing for it. It holds no copy of the rooms: `hub::search_results` makes the rows from the current account's cache under the hub's lock, and the model resets on every new result set, on `Event::Directory`, `Event::Rooms` and `Event::QuietRooms`, and on an account switch (`switched`, which also searches the new account's directory for the text). `setQuery` asks the core to search the directory (`hub::search_directory`) on every change of the text, which is `AccountHandle::search_directory`'s contract; `retry` is the same call again. A directory action under way (`Event::DirectoryAction`, `set_busy`) changes the `busy` role of its row alone.
- **Cursor:** the model's `cursor` property is the row Enter acts on, always one that can be acted on (or -1). `cursorUp` and `cursorDown` skip labels and status rows; a new search puts it on the best match, and a refresh of the same search keeps it on its row if that is still there. `open(row)` and `openCursor()` act on a row: a room opens, a person is `open_direct`, a channel `preview_channel`, and they say whether they did, so that the field clears itself and gives the focus on as it does for a room. A person or a channel is not acted on while another directory action is under way, as the core would ignore it, so the field stays.
- **The room:** `Room` (`room_vm.rs`) has `preview` (the open room is a channel the user looks at without being in it) and `joining`, from `RoomState` (`rc_view::room_view::with_preview`, over `Cache::preview()` and `Cache::directory_action()`): the header takes its name, kind and topic from the preview while the room list lacks the channel, and `Room.join()` is `join_channel`. `Event::Preview` and `Event::DirectoryAction` tell it. `send` refuses while `preview`, so Enter in the composer keeps what is typed. A directory action's failure goes to `RoomList.roomActionError`, the strip the room menu uses, whose Dismiss is the same, and the search stays; a new action clears it.
- **QML:** in `RoomPage.qml` the results list `roomSearchResults` picks a delegate by `rowType` (`DelegateChooser`): `RoomDelegate` for a room, as before (`searchResult_<id>`), `DirectoryRow` for a person (`directoryPerson_<username>`) and a channel (`directoryChannel_<roomId>`), `DirectoryLabel` (`directoryGroup_people`, `_channels`, `_rooms`) and `DirectoryNote` for the searching row (`directorySearching`, with a spinner), the failed row (`directoryError` and the Retry button `directoryRetry`) and the more line (`directoryMore_people`, `_channels`). A row has the look and height of a room's. A person shows the name, then the username in faint small type if it is another, elided together, and at the right `directoryHint` ("Message") while the pointer or the cursor is on the row, `directoryBusy` ("Opening…") while its action is under way, always visible then. A channel shows `directoryMembers` ("N members") there, `directoryHint` ("View") in its place while the pointer or the cursor is on it. With nothing to show, once the directory has answered, `roomSearchEmpty` says `No rooms, people or channels match “<query>”`. In `Composer.qml` the Join button `composerJoin` takes Send's place while `Room.preview` (not in a thread's composer), says "Joining…" and is disabled while `Room.joining`, and the field stays usable. The tokens are `Theme.directory*`.
- **Tests:** `crates/rc_gui_tests/tests/directory.rs` runs the app with `RC_DIRECTORY_DEBOUNCE_MS=0` (and a long pause for the searching row), on its own users and channels under a name prefix unique to the test, since the server has tens of thousands of channels: the groups and their order, that the user's own channels and direct message partners are not offered, messaging a person (the direct message is listed and the person leaves the directory), the keyboard, the preview with its messages, Join and live messages, joining (the channel is listed as the open room, Send is back, the draft is kept and then sent), opening another room ending the preview, "N more", the no-match line, the searching row, and the unreachable directory with its Retry (through the test `Proxy`). The "Opening…" look needs a server that is slow to answer; `SearchRow::is_busy_with` is unit-tested in `rc_view` instead.

## Slint side

The same behaviour and element names as the Qt side, from the same `rc_view` rows; every test of `directory.rs` runs against `rocketchat_slint` unchanged.

- **Model:** `RoomSearchModel` (`rc_slint/src/room_search_model.rs`) holds the `rc_view::directory::SearchRow`s, kept bottom to top like the Qt model so that `first_actionable` and `next_actionable` apply as they are, the avatars, the directory action under way and the cursor. It gives the view rows of the Slint struct `SearchRow` (a `SearchKind` and the fields the kinds read: `room` for a room, and for a person or a channel its id, name and avatar; `username`, `members`, `busy`, `group`, `count`, `text`), top to bottom, which is what the bottom-aligned `for` lays out (see [Slint side](room-list.md#search)). `app.rs` replaces it as a whole (`show`) on a new query, `Event::Rooms`, `Event::QuietRooms`, `Event::Directory` and an account switch (which also searches the new account's directory); the cursor stays on its row for all but a new query, as in Qt. `Event::DirectoryAction` changes the `busy` of its row alone (`set_busy`) and shows the failure in `roomListError`, which the next action clears; `Event::Avatars` changes the rows that show the file.
- **Cursor:** it is the model's, and `app.rs` gives the view its index (`search-cursor`); Up and Down of the field are `search-cursor-up` and `-down`, Enter and a click `open-search-row(index)`, which says whether it acted (a person or a channel isn't while another action is under way), so that the page clears the field and wishes the composer the focus, as for a room. Retry is `retry-search`, which asks the core for the field's text again. A row that gets the cursor tells the list where it is (`changed cursor`), which scrolls to it; a new result set shows the bottom.
- **Views:** `room_search_results.slint` has a `ResultRow` per row, which picks by kind: `RoomDelegate` for a room, `DirectoryRow`, `DirectoryLabel` and `DirectoryNote` (`directory_row.slint`) for the rest. The rows have the heights of their kind (`Theme.directory-*`, the same values as Qt's tokens). The label's text is made upper case in Slint (it has no text transform) and keeps the words as its accessible label, which is what the tests read.
- **Preview and Join:** `show_room` gives the page `room-preview` and `room-joining` from `RoomState`. The room composer's one button is Join (`composerJoin`, "Joining…" and disabled meanwhile) in place of Send (`composerSend`) while `preview`, the same box and look; Enter does nothing then, so the draft stays. The thread pane's composer never has it.

## Tests

`crates/rc_core/src/client/tests/directory.rs` runs the actor on the fake server and clock: the pause and the newer text, the answer that is dropped, the clear, the retry, the expired token, the logout in every state, the direct message with the push before and after the answer and for a quiet room, and the preview opened, left, cancelled, joined (with the push before the answer) and kept through a reconnect. `crates/rc_view/src/directory.rs` tests the view. The contract tests pin the server facts above, including the live updates for a user who is not in the channel (`crates/rc_api/tests/contract.rs`) and the whole flow through the core (`crates/rc_core/tests/contract.rs`).
