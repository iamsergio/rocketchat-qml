# Directory

The room list's search field (ROOM-010, [Search](room-list.md#search)) finds the user's own rooms locally and at once. The server's directory adds to it: the people the user has no direct message with, and the public channels the user is not in. Opening a person starts a direct message (ACT-007); opening a channel previews it, and the user may join (ACT-008). This is the core and `rc_view` part; the screens are not here yet (see [PLAN.md](../../PLAN.md)).

## What the server does

The contract tests (`crates/rc_api/tests/contract.rs`, `crates/rc_core/tests/contract.rs`) record it. Checked on Rocket.Chat 8.0.

- **Directory:** `GET /api/v1/directory?text=<t>&type=users|channels&workspace=local&count=N&offset=0`, with `sort={"usersCount":-1}` for channels. `text` and `type` are parameters of their own: the older `query={"text":..,"type":..}` is ignored on Rocket.Chat 8 and the server then lists every room (70,219 on the test server). The answer holds the entries as `result`, and `total`. A user has `_id`, `username`, `name`, `createdAt` and `emails`, which `rc_api` drops. A channel has `_id`, `name`, `fname` (only if it differs), `t`, `usersCount`, `ts`, `default`, `lastMessage` and a `topic` if it has one; it has no `avatarETag`. Only public channels are listed, never a private group. The directory does not say whether the user is in a channel.
- **Direct message:** `POST /api/v1/im.create {"username"}` answers `{"room":{"_id","rid","t":"d","usernames"}}`. It is idempotent: the same room the second time, and a direct message the user had closed is opened again (`subscriptions.getOne` has `open: true` after). **It does not check the username**: an unknown one makes an empty direct message with a name nobody has. So the core only asks for usernames the directory gave.
- **Joining:** `POST /api/v1/channels.join {"roomId"}` answers `{"channel":{..}}`, and succeeds for a channel the user is in. A private group or a room that doesn't exist is a `Server` error. The join adds a system message to the channel and a subscription with one unread message and a mention. The server pushes the subscription.
- **One subscription:** `GET /api/v1/subscriptions.getOne?roomId=` answers `{"subscription": null}` for a room the user is not in. The subscription lacks the time of the last message, the avatar's etag and the topic, which `rooms.info` has, so `RestSession::subscription` asks both, as `subscriptions` does with `rooms.get`.
- **Looking without being in:** a user who is not in a public channel (permission `preview-c-room`, granted to `user`) can read `rooms.info`, `channels.history` and `chat.syncMessages` of it. A private group is refused.
- **Live updates without being in:** all three arrive for a user who is not in the channel, on the streams the core has open already. The messages come on `stream-room-messages` with `__my_messages__`, which carries the messages of every public channel (not those of private groups), and also the join messages of everybody in `GENERAL`. The deletions (`<room>/deleteMessage`) and the typing (`<room>/user-activity`), which the core follows for the open room, are accepted for such a channel. So a preview needs nothing new on the connection: no subscription to the room, no polling.

## Searching

`AccountHandle::search_directory(text)` is called on every change of the field's text. The core:

- trims the text; an empty one cancels the pause and the request and clears the results;
- tells the frontend at once with `Event::Directory` (the query, state `Searching`, no results), and waits for the typing to stop (300 ms; `Tuning::directory_debounce`, `RC_DIRECTORY_DEBOUNCE_MS` in whole milliseconds, `0` for no wait: a testing aid) before it asks. The wait is a deadline of the actor (`next_deadline`), not a timer task, so it runs on the fake clock in tests;
- then asks the users and the channels in parallel, 10 of each (`RESULTS_PER_KIND`: a frontend shows 5 of each, and the user's own rooms among the answers are filtered out of the 10), in one task;
- a newer text, or a clear, ends the request in flight and the answer of a request that was ended is dropped by its attempt id; so is the answer after a logout;
- answers with `Event::Directory` in state `Ready`, with the people, the channels and the server's totals, or `Failed` with a text (`DirectoryError`: "Can't reach the server's directory", or the server's message). An expired token expires the session, as everywhere;
- wants the avatars of the people (`AvatarOwner::User`) and of the channels (`AvatarOwner::Room`), like the room list's: the download asks the server whether there is one, and the 20 rows are cheap;
- the same text again does nothing, whatever the state, except after a `Failed`: then it asks again at once, without the wait. That is the **Retry**: the frontend calls `search_directory` with the field's text again.

A logout clears the search (an `Event::Directory` with the empty query, if it held anything).

## What is shown

`rc_view::directory::directory_view(result, listed, quiet, own_username)` (and `Cache::directory_view()`, over the account's cache) is a plain function, so both frontends show the same. The core's result is the server's, whole. The view leaves out the user and the people with a direct message with them (a quiet one too: its `peer` is the other user's username; usernames compare without regard to case), and the channels whose id is one of the account's rooms, the quiet ones included, then keeps 5 of each. `people_more` and `channels_more` count what the server has beyond what it sent, plus what the cut dropped: "N more, keep typing". They are an upper bound, since some of the entries beyond may be rooms the user has. The view is recomputed whenever the room list changes (`Event::Rooms`, `Event::QuietRooms`), with no new search, so a channel just joined or a direct message just opened drops out.

`Cache` keeps the last `Directory` (`directory()`), the last `DirectoryAction` and its state (`directory_action()`) and the previewed room (`preview()`), reset to nothing when the session ends. The switchboard routes the new events like the others.

## Actions

Each is a command of `AccountHandle` and answers with `Event::DirectoryAction { action, state }`: `Working` when it starts, then `Done`, or `Failed(RoomActionError)`, whose text is meant to be shown as it is, in the room list's error strip, as the room menu's. The busy look ("Opening…", "Joining…") is `Working` for that action in `Cache::directory_action()`. One runs at a time; a command that comes while another is under way is ignored (logged at debug), so the frontend keeps the row busy and the others inert. The answer of an action whose session ended is dropped (attempt id); nothing comes then, and the cache forgets the action. An expired token expires the session. All three are ignored unless logged in.

- **`open_direct(username)`** (`DirectoryAction::OpenDirect`): `im.create`, then `subscriptions.getOne` and `rooms.info` for the room, which goes into the room list (`upsert_now`) without waiting for the realtime push, and then the room is opened like any (`open_room`). The push, before or after, changes nothing: the room is the same. A direct message that went quiet (ROOM-008) comes back as the open room, as when it is opened from the search. Order: `Rooms` (the insert, if new), the events of opening the room, `Done`.
- **`preview_channel(room_id)`** (`DirectoryAction::Preview`): a channel the room list has is just `open_room`. Else `rooms.info` builds a `Room` (a public channel only; anything else is a failure), and the channel opens as the open room though the room list lacks it. `Event::Preview(Some(room))` comes first, for the header, then the events of opening the room, then `Done`. Nothing is marked read (it has no subscription), it is not in `Rooms`, `Unread` or `QuietRooms`, and a frontend keeps it out of the room search. Everything of an open room works: history, live messages, deletions, typing, and the catch-up after a reconnect (a preview is not closed for lacking a subscription). Sending is refused, as for any room the list lacks. The preview ends, with `Event::Preview(None)`, when another room is opened (the user stays out of the channel), the room is closed or the session ends, and when the room list has the channel (after the `Rooms` event that lists it, so also when the user joined from another client). A preview still on its way when another room is opened is cancelled (`Done`).
- **`join_channel(room_id)`** (`DirectoryAction::Join`): `channels.join`, then the subscription as above goes into the room list. If the channel is the preview, it stays the open room: the timeline is not reset (no `Timeline` event comes), the room is read as any open room, and `Preview(None)` comes after the `Rooms` event that lists it. Ignored for a channel the list has. A failure leaves the preview as it was.

## Tests

`crates/rc_core/src/client/tests/directory.rs` runs the actor on the fake server and clock: the pause and the newer text, the answer that is dropped, the clear, the retry, the expired token, the logout in every state, the direct message with the push before and after the answer and for a quiet room, and the preview opened, left, cancelled, joined (with the push before the answer) and kept through a reconnect. `crates/rc_view/src/directory.rs` tests the view. The contract tests pin the server facts above, including the live updates for a user who is not in the channel (`crates/rc_api/tests/contract.rs`) and the whole flow through the core (`crates/rc_core/tests/contract.rs`).
