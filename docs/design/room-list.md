# The room list

- **Order and sections:** `rooms::display_order` puts the user's favorites first, and orders each group by last activity (most recent first), then name (ignoring case), then id. The list is one list: a favorite that is set or taken back is an `upsert` whose position changes, which comes out as a `Moved` change (or `Updated` if it stays where it is), like any other change of order; a message in a room that is not a favorite moves it up only as far as the first non-favorite. `Room.favorite` comes from the subscription's `f`, which is absent for a room never favorited; `subscriptions.get` and the subscription the server pushes are the same wire type, so a favorite set by another client arrives live.
- **Sections:** the GUI shows the headings "Favorites" and "Rooms" only while there are favorites, so a user without any sees a plain list.

## The room menu

Right-click on a row. Its rules are the core's, so a frontend only offers what the core will accept:

- **Add to / remove from favorites:** all rooms.
- **Mark as read** when the room shows something unread (`Room::has_unread`: unread, mentions or alert), else **mark as unread**. The open room stays read while it is open (ROOM-004), so marking it unread is refused by the core and the menu doesn't offer it.
- **Leave:** channels and private groups (`Room::can_leave`), after a confirmation naming the room. Direct messages can't be left.

## Server calls and what they push

`Client::set_favorite`, `mark_read`, `mark_unread` and `leave_room` end in one `Event::RoomAction` (room, `RoomAction`, and `Ok` or a `RoomActionError` with a text to show), as for messages. A room that is not in the list, a direct message to leave and the open room to mark unread are refused at once, without a request. Ignored when logged out; an answer after a logout is dropped; a dead token ends the session.

- `POST /api/v1/rooms.favorite` with `roomId` and `favorite`. The request says which of the two is wanted, so repeating it changes nothing. The server refuses a room the user isn't in ("You must be part of a room to favorite it"). It pushes the subscription with `f`.
- `POST /api/v1/subscriptions.read` with `rid` (the call opening a room makes too): zeroes the counts and the alert.
- `POST /api/v1/subscriptions.unread` with `roomId`. Whatever the number of messages, the subscription ends with `unread` 1 and `alert` true, the mentions untouched (it counts from the newest message of somebody else); calling it again changes nothing. A room without messages is refused ("There are no messages to mark unread [error-no-message-for-unread]"). The change is pushed.
- `POST /api/v1/channels.leave` or `groups.leave` with `roomId`, by the kind of room (the other one answers "room not found"). The subscription is removed and pushed as removed. The last owner of a room is refused with "You are the last owner. Please set new owner before leaving the room. [error-you-are-last-owner]", which is shown as the server words it, after "The server reported an error: the server answered 400:".

## Applying at once

On success the core applies the change to the room as it is by then, without waiting for the push, which then changes nothing: a favorite is set, not toggled; mark read clears the counts and the alert (`Room::read`); mark unread sets `unread` to at least 1 and the alert, which is what the push says; leaving removes the room, and closes it if it was open, as a removal that the server pushes does. A room opened meanwhile stays read, as for any change of the open room. An answer for a room that has gone changes nothing.

## Qt side

- **`RoomList` model:** roles `favorite`, `hasUnread` and `canLeave` besides the old ones, and the properties `hasFavorites` (recomputed after each batch of changes, announced when it flips) and `roomActionError` (the text of the last failure, cleared by the next command and by `dismissRoomActionError`). The invokables `setFavorite`, `markRead`, `markUnread` and `leave` take a room id. The model gets `Event::RoomAction` from the hub like the `Room` view model gets message actions.
- **QML:** one `ListView` with `section.property: "favorite"` (a bool section value is the text "true" or "false"). The section item always exists and has no height without favorites, because the view decides whether it is visible. Menu items take their text and visibility from the roles, with no branching in QML: `roomMarkReadAction` is visible when `hasUnread`, and `roomMarkUnreadAction` when not `hasUnread` and the row is not the open room. The menu and the confirmation are parented to the window's overlay while open.
- **Spix:** the menu opens with a right-click (`MouseArea`, as `TapHandler` doesn't react to Spix clicks) on the row `room_<id>`; its items and the dialog are addressed from the window and exist only while open. A test closes the menu with Escape. See [GUI testing contract](gui-testing.md) for the names.

## Slint side

- **Rows:** `RoomRow` has `favorite` and `can-leave` (from `Room::can_leave`) besides `has-unread`; the menu offers what they say, with the open room excluded from "Mark as unread" as in QML.
- **Menu:** `room_delegate.slint` has a `PopupWindow` at the pointer, opened by a right-click (`pointer-event`), of `MenuItem`s. Slint keeps a popup inside the window, so a row near an edge needs nothing of ours. The three conditional items are always there and take no height while hidden (`visible` and a height of zero): an `if` item in a popup is not clicked where the test backend aims (SLINT.md).
- **Leaving:** the item only asks: `main.slint` holds the room's id and name and shows `confirm_dialog.slint` (a generic confirmation, here asking to leave), which dims and blocks the whole window (Escape cancels). Confirming calls `leave-room`.
- **Errors:** `room-list-error` of the window is the text of the last failed `Event::RoomAction`, cleared by the next command (set to empty in `app.rs` before each one) and by the Dismiss button; it shows as `roomListError` under the list. It is a few lines, so it is not shared with `rc_qt`'s model.

## Search

A field below the room list, at the bottom of the sidebar (Ctrl+K focuses it) finds the user's own rooms by name. It is local: no server call, so it finds what the account has: the rooms of the list and the quiet direct messages the list holds back (ROOM-008), which is how an old direct message is found by name. Searching the directory, for people and channels the user isn't in, comes later and will add to this field.

- **Matching:** `rc_view::room_search::search_rooms`, a plain function of the listed rooms, the held-back rooms and the query, so Slint can use it too. The query is trimmed, and an empty one is not a search. Case and accents don't matter (`unicode-normalization` takes the combining marks off the decomposed text). A room matches by the name the list shows and, for a direct message, by the other user's username too. The rooms whose name starts with the query come first, then those that contain it, each group with the listed rooms first, in the list's order (favorites first, then the most recent activity), and then the held-back ones, most recent activity first. So a quiet `alice` is above a listed `the-alice-room`, and a listed `alice2` is above a quiet `alice`. The core sends the held-back rooms already in order (`Event::QuietRooms`, below), so nothing sorts them.
- **Held-back rooms:** `Event::QuietRooms(Vec<Room>)` carries all of them, most recent activity first, then by id. It comes after the `Rooms` event that changes the set or the content of one of them (a room that goes quiet is `Removed` first, one that comes back is `Inserted` first), and after a logout empties it; never while the set stays as it was, nor while it is empty from the start. It is the whole set, not changes, since it changes rarely and has no positions. The account compares it with what it last sent after every change of the room list, including the changes the list doesn't show (a held-back room renamed, or with a new topic or time, that stays held back), and `rc_view`'s cache keeps the last one. The room list says when the held-back rooms may have changed (`RoomList::take_quiet_change`), so the account compares them only then, and a message in a shown room costs nothing here. The rooms that join the set show the avatar file the cache holds (`Avatars::show_cached`, see [Avatars](avatars.md)) and nothing is downloaded for them, since an account may hold hundreds and the downloads would queue ahead of the avatars the user looks at; one without a cached file shows initials. The avatar is wanted and downloaded as for any room when the room comes back with an `Inserted`.
- **Qt side:** the `RoomSearch` model (`RoomSearchModel`), next to `RoomList`, which it doesn't touch. It holds the query (`setQuery`), `active` (whether the query is not empty) and the results, and keeps no copy of the rooms: it asks the hub, which searches the current account's cache (`hub::search_rooms`, over the listed and the held-back rooms, under the hub's lock). It has the roles of `RoomList` (`room_roles.rs`). It resets whenever the query changes, and whenever the room list or the set of held-back rooms changes (`Event::QuietRooms`) or the account switches while `active` (the hub queues a `refresh`, which does nothing otherwise), which is the one place a model resets: a new query is a new result set. An account switch searches the new account's rooms, held-back ones included, for the same query. Opening a held-back room from the results is `open_room` like any other: the core shows the room again (an `Inserted`) because it is the open room. `open(row)` opens the room in the row and says whether there was one.
- **QML:** the field and the results list `roomSearchResults` are in `RoomPage.qml`. While `RoomSearch.active`, the results are visible and the room list is not. The results pile up from the field: `roomSearchResults` fills the area of the list but is laid out `BottomToTop`, so the best match is right above the field and a few results sit next to it, with the space above empty. The rows are the same `RoomDelegate`, named `searchResult_<id>`, with no context menu. The open room is `highlighted` there as in the list; the keyboard cursor is a different look, `cursor` (the pointer-over fill), which the open room's look wins over. The focus stays in the field: Up and Down move the cursor as the screen shows it, Up away from the field to the next result and Down back (it is on the first result, the best match, after each reset), Enter opens that result and clears the field, Escape clears it, and so does a click on a result; each of the three then moves the focus to the composer of the open room (to nothing if no room is open), so the field is at rest with its hint, while the clear button keeps the focus in the field. With no match `roomSearchEmpty` sits just above the field and says `No rooms match “<query>”`, with `RoomSearch.trimmedQuery`.
- **Slint side:** `RoomSearchModel` (`rc_slint/src/room_search_model.rs`) holds the rooms found and nothing else: `app.rs` runs `search_rooms` over the current account's cache on the GUI thread, on each change of the query and, while it isn't empty, on `Event::Rooms`, `Event::QuietRooms` and an account switch, and replaces the model as a whole (a reset), bumping `search-generation` so that the view puts its cursor on the best match. The rows are stored worst first, because the view lays them out top to bottom and the best match is the last row, right above the field. `room_search_results.slint` is a plain `for` in a bottom-aligned `VerticalLayout` in a `Flickable`, since the lazy `ListView` can't bottom-align (SLINT.md), so every match is instantiated: 500 matches (a one-letter query on a big account) take about 3 ms in a release build and about 20 ms in a debug build, to make and lay out the rows, and each search replaces them all. The room list and the results share one stretching area, and the list is `visible: false` while searching, which the tests see as hidden. The focus stays in the text input: a `FocusScope` around it takes Up, Down, Enter and Escape in `capture-key-pressed`, and a `FocusScope` around the page takes Ctrl+K. Giving the focus on is a wish of the page (`composer-wanted`): the composer takes it when it is made or when the room changes, or at once when asked again (`focus-requests`), and the message list, which takes the focus when a room opens, leaves it alone while the wish stands; with no room to hand it to, the field just gives it up.
- **The field:** the last thing in the sidebar column, below the room action error strip. Its vertical centre is on the one of the rail's settings button (`Theme.searchFieldBottomMargin`). An `InputField` with `quiet` (no border and a darker fill until it has the focus). Its text starts where the room names do and the magnifier is centred over the avatars, both from the row's own tokens (`Theme.roomNameInset`, `Theme.roomAvatarCenter`). At rest it shows a keycap with "Ctrl K" (`roomSearchHint`); with text, a cross (`roomSearchClear`) that clears the field and leaves the focus in it.

## Batched channels

So that channels don't distract, the room list shows their news in batches, at most once every 25 minutes (ROOM-011). It lives in `rc_core::rooms::RoomList`, so both frontends get it unchanged.

- **The rule:** for a channel or a private group (favorites too), the news is what the user notices in a row: more unread, the alert, newer activity, new unread threads. When the server pushes news, the row keeps showing the room as it was (no bold, no count, no move) and the rest of the push still shows at once (name, topic, favorite, avatar). The real state waits in `pending`, one room per id, the latest.
- **One timer:** `held_since` is the time of the first change held since the last release. `next_release()` is that plus the interval, and the actor's `next_deadline` includes it next to the quiet one, so no timer runs while channels are quiet. At the deadline `release_channels` calls `RoomList::release`, which shows every held room in one go, moved into place, and ends the batch. The next held change starts a new one. The user is interrupted once per interval at most.
- **Never held:** direct messages (group ones too); a room with a mention (`user_mentions` or `group_mentions`, so `@all` and `@here` too), which also shows that room's held news; the open room, and opening a held room shows it whole; a room that becomes read (the held news is dropped); a room the list didn't know; what the user does from the room menu (`upsert_now`, used by `change_room`); and the list after login or resume (`reset`). `remove` and `reset` forget the held news.
- **`get` and the shown row:** `RoomList::get` gives the real state (the `pending` entry first), because callers merge pushes onto it: the subscription push copies `last_activity` from it and `bump` compares against it, so a held bump is not lost whichever comes first. `rooms()`, the `RoomChange`s and `unread()` are about what is shown. So the server tile's badge does not give a held channel away either, and room search, which uses the shown rooms, finds a channel under the name and position it shows.
- **Tuning:** `Tuning::channel_batch`, `rooms::CHANNEL_BATCH` (25 min), overridden in whole seconds by `RC_CHANNEL_BATCH_SECS`; `0` turns batching off. The core test harness turns it off, and the GUI test harness sets `RC_CHANNEL_BATCH_SECS=0` unless a test passes its own to `App::launch_with`. The interval is to come from the settings dialog (PLAN.md, Phase 6).
- **Desktop notifications (Phase 6)** are to follow the shown state, so they don't give a held channel away either.
- **Tests:** `rooms.rs` (the list, with explicit times), `client/tests/batch.rs` (the actor on the fake clock) and `realtime.rs` in the GUI tests. The GUI test tells a bold row through the room menu (`shows_unread` in `tests/common/mod.rs`: "Mark as read" is offered only for a room that shows unread), as a channel's non-mention news has no number.
