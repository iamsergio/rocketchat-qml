# Edits, deletions and reactions

The server tells an edit or a reaction by pushing the whole message again on `__my_messages__`, with `editedAt` for an edit, and the `reactions` it has now (absent once the last one is taken back). Rocket.Chat pushes a deletion on no stream of the user's: only `stream-notify-room` with `<room id>/deleteMessage` carries it, for a room that was subscribed to. Bulk deletions (`deleteMessageBulk`) are not followed ([PLAN.md](../../PLAN.md), Issues).

- **Replacing:** a message the timeline holds as confirmed is replaced by a pushed or paged copy that differs (`Timeline::replace`), as an `Updated` change, or `Moved` if its time puts it elsewhere. A copy that is equal changes nothing. Copies are whole, so reactions are replaced, never merged. A pushed copy of a message older than everything held, while older ones exist but are not held, is dropped: inserting it would leave a hole between it and the rest. The same message is then shown when its page loads.
- **Removing:** `Timeline::remove` gives a `Removed { index }` change, which the message model turns into `beginRemoveRows`/`endRemoveRows` (and a `dataChanged` of the next newer row, whose day separator depends on the removed one). The actor applies a deletion to the room's messages whether it is open or only held. It remembers the ids deleted while the room is open, so that a page that was asked for before the deletion doesn't bring the message back.
- **Following the open room:** the forwarding task owns the `DdpClient` and a deletion subscription (`subscribe_room_deletions`, ended with `unsubscribe`, which sends `unsub` and doesn't wait for the answer). The actor sends it the open room (`Some(room)`, or `None` once it closes) when a room opens or closes and after each new connection is up; the task ends the previous room's subscription and starts the new one's. A room that can't be subscribed to is logged and nothing else: edits and reactions still arrive, and the catch-up removes what was deleted.
- **Catch-up:** `RoomHistory::synced_at` is the client's clock just before the request that last brought the room up to date: the catch-up below, or the newest page of a room that had none. When the room is opened, and when the connection comes back with a room open, the actor also asks `chat.syncMessages` (`ServerApi::changes_since`) for what changed since `synced_at` minus a minute, which covers the difference between the clocks (applying a change twice does nothing). The messages it lists as updated replace the held copies, those it lists as deleted are removed, and the others are left to the newest page. `synced_at` moves forward only when the catch-up succeeds, so a failed one is asked again from the same time. Its answer carries an attempt id and is dropped if the room was closed or another request began, like a history page's.
- **Qt side:** the `MessageList` model has an `edited` role and a `reactions` role, a list of maps (`emoji`, the shortcode; `glyph`, its Unicode text; `image`, the URL of a custom emoji; `count`; `mine`, whether the viewer reacted; `users`, comma-separated, for a tooltip), made by `reaction_view` and drawn again when the viewer or the custom emoji change. The delegate shows "(edited)" next to the time and a chip for each reaction below the attachments; reacting from the GUI is in [Reacting](reacting.md).
