# Jumping to a message

Choosing a result of the [message search](message-search.md) shows that message in the room, even when it is far older than what the room holds (MSG-008, step 3). This is the target design of the whole step; it is built in five parts (see Steps), and all of them are done: the open room's fetch has a kind and its timeline goes to the store through one function, the server calls and their ports exist, the core has the detached window, the Qt side shows it, and thread replies open their thread. Slint (step 5 of the search) is not built yet.

## What the user gets

- Clicking a result, or Enter on the one under the cursor, scrolls the room to that message and marks it (a tinted background and a bar at its side). The search pane stays open, with the result marked as picked.
- If the message is not among those the room holds, the room shows a window around it. Scrolling down loads the newer messages until the window joins the latest ones; a pill "Jump to latest" shows while the room is cut off from the latest messages, and so does End.
- A message that no longer exists says "This message no longer exists" in the search pane and leaves the room as it is.
- The mark goes when the user jumps again, jumps to the latest, sends a message, opens another room or the message is deleted. Closing the search pane keeps it. It does not fade.
- A reply in a thread shows its parent in the room (or the reply itself if it was also sent to the room), with the mark, and opens the thread in the pane over the results; Back returns to the results. The thread does not scroll to the reply.

## What the server does

Checked on Rocket.Chat 8.0.1. Today's history is REST only (`RestClient::history`, `ServerApi::history`), and REST has no "around a message": `channels.history?oldest=X&count=n` returns the newest n after X, so it cannot walk forward either. The DDP methods are reachable through REST `method.call`, which the client's private realtime task does not need to share.

- `POST /api/v1/method.call/loadSurroundingMessages` with `{"message": "<DDP method frame as a JSON string>"}`, the frame being `{"msg":"method","id":"7","method":"loadSurroundingMessages","params":[{"_id":"<id>"},<limit>]}`, answers `200 {"message": "<DDP JSON>", "success": true}`. The inner `result` is `{messages, moreBefore, moreAfter}` with EJSON dates, which `wire.rs` already parses. The order is floor(limit/2) older messages newest first, then the target, then up to ceil(limit/2) - 1 newer ones oldest first; at an edge the other side is not filled up. It finds the message by `_id` only, and includes thread replies not sent to the room (the core filters them with `shows_in_room`). A missing or deleted id is a `200` with `result: false`, and so is the id of a message in a private group the user is not in (the server does not say that it exists). A bad argument is a `400` with the DDP `error` inside `message`; a bad token is a `401`. It works for channels, groups and direct messages.
- `loadNextMessages(rid, {"$date": ms} | null, limit)` answers the messages with a timestamp after the given one (exclusive), oldest first, hidden thread replies included, with no "more" flag. For something that is not a room it is a `400 error-not-allowed`.
- `chat.getMessage` is a `400` for a deleted message.

In `rc_api` (built): a private `RestSession::method_call(name, params)` that decodes the inner frame and maps its `error` (in a `400` or a `200`) to `Error::Server` with the error's `reason`, a `401` to `Unauthorized` and any other non-2xx to the REST mapping; `surrounding_messages(id, limit)` giving `Option<Window { messages, more_before, more_after }>` (`None` for `result: false`), which `wire.rs` sorts oldest first, the one place that knows the server's order; `next_messages(room, after, limit)` giving a `NextPage` (a `HistoryPage` has `reached_start`, so not that one), whose `reached_end` is the raw length being below the limit, counted before the filtering as `parse_history` does. The core asks from `newest.ts - 1 ms`, and the timeline de-duplicates. The ports are `ServerApi::around` and `ServerApi::newer` (`MessageWindow`, `NewerPage`), whose REST adapter leaves out the thread replies the room does not show as `history` does, after the flags were taken; the fake serves both from the messages it is given for a room (`set_room_messages`) unless a script is queued. A `429` (the DDP rate limit, when enabled) is an error like any other.

## What the core does

- **The window.** `Timeline` gets `detached`: newer messages exist that it does not hold. It is not part of `RoomHistory`, so it is never stored. The open room's fetch (`Fetch`) has a `FetchKind`: `Newest`, `Older`, `Newer` and `Around(MessageId)`; its answer is a `Fetched` (a page, a window or a newer page). `OpenRoom` gets `found: Option<Found { message, state }>`, the state being `Loading`, `Shown` or `Missing`. `Timeline::merge_window` takes the window in: if it shares a message with what is held the two merge and `detached` is cleared when the window has nothing after it (`more_after` false), else it replaces the messages (unsent ones go too: they are in the stored copy) and `detached` is `more_after`.
- **Commands.** `AccountHandle::show_message(id)`, `load_newer()` and `show_latest()`.
- **show_message.** If the timeline holds the target, there is no request: `found` is `Shown` and `Event::ShowMessage` follows (a jump still loading is dropped). Otherwise the fetch in flight is aborted (attempt ids, the last wins; a fetch of older messages or of a window's next page is not), `found` is `Loading` and the core asks `around(id, page size)`. The answer replaces the window; if it shares a message with what is held, the two merge and the timeline stays attached. `result: false`, and a window without the target (a thread reply the room does not show, until 3e), make `found` `Missing` and leave the timeline alone. A failed request clears `found` and sets the error like a failed page: "missing" would say something about the message. If the jump cut short the fetch of the newest page, that fetch is made again when the room ends up attached. The page size is `PAGE_SIZE`; `Client::start_with_page_size` (hidden) sets it for tests of the real server, which would need hundreds of posts otherwise.
- **The store.** `OpenRoom::persist` is the one place the open room's timeline goes to the `MessageStore` (done in 3a); the window is never saved while detached, so the store keeps the attached copy. While detached, `change_timeline` applies the changes (edits, deletions, echoes settling, delivery failures) to the window, emitting them, and to the stored copy, as it does for a closed room. Pushed new messages go to neither: `merge_live` on a detached timeline drops what it does not hold. Unread counts and notifications come from the subscriptions and are not affected.
- **load_newer** appends pages (`Appended`) until a page reaches the end or reaches a message the stored copy holds. Then it joins: appends the rest (when the page reached a stored message, the stored copy's messages after the page come along, so that the newest page cannot miss the window), clears `detached`, and fetches the newest page with the catch-up, as opening a room does. The page carries the time of its last raw message (`NextPage.last`, `NewerPage.last`), taken before the replies the room does not show are left out; the open room keeps the furthest of them (`newer_to`) and asks from the later of that and its newest message, so a page of hidden replies cannot be asked for twice. It is forgotten when the window is replaced, joins or is left. `load_older` is as today, with `reached_start` from `moreBefore`.
- **show_latest** resets to the stored copy, then fetches the newest page; the status (`detached` false, `found` none) comes before the reset. On an attached room it only clears `found`. Sending runs it first. A reconnect while detached only runs `fetch_changes` for the window (`sync.rs`), as does one while a jump is loading (the fetches go over REST, which the lost connection did not touch); the catch-up of a detached window is applied to the stored copy too, which then gets the new `synced_at`, and it clears `found` when it deletes the found message. Opening another room and coming back opens at the newest: the jump is forgotten.
- **Events.** `Reset`, `Prepended` and `Appended` are reused. `TimelineStatus` gets `detached`, `loading_newer` and `found`, emitted before the window's reset. A one-shot `Event::ShowMessage { room, message }` follows the change that brings the target in; the cache does not keep it.

## The highlight

The state is the core's `TimelineStatus.found`. `rc_view::MessageList` holds the found id, and `set_found` returns the rows to announce, as `set_viewer` does. The search row's `picked` comes from it. It clears on another jump, `show_latest`, sending, another room or closing the room, and the deletion of the message; not on closing the search pane.

## What the Qt side does

As built (3d):

- **`rc_view`.** `MessageList` holds the found id (`set_found` returns the runs of rows to announce, the one that was marked and the new one; `is_found`, `row_of`). `Cache::found` gives the core's `TimelineStatus.found`. `RoomState` has `detached`, `loading_newer`, `follows_newest` (not while detached) and `show_jump_to_latest`. `message_search_view` has `pick_state` (a row is picked while its message is `Loading` or `Shown`, and opening while `Loading`) and `missing_note`.
- **`rc_qt`.** The hub tells the `MessageList` model `set_found` on every `TimelineStatus` (in the model's own queue, before the window's reset) and `request_show` on `Event::ShowMessage`, which emits `showRequested(row)` if the model holds the message. `MessageMirror` has the `found` role. `RoomVm` has `detached`, `loadingNewer`, `followsNewest`, `showJumpToLatest` and the invokables `loadNewer` and `showLatest`. `MessageSearch.pick` calls `show_message`; the model keeps the core's `Found` (the one copy it reads `picked` and `opening` from), a `missingNote` property, and hides the note once the text changes. `show_all` (an account switch) tells the `Room` view model before the list, which reads `followsNewest` when it resets.
- **`RoomView.qml`.** A model reset sets `followsNewest` from `Room.followsNewest`; `showRequested(row)` clears it and calls `positionViewAtIndex(row, ListView.Center)`. The bottom of a detached list (reaching it by the wheel, a drag of the scroll bar or Page Down, or a content that does not fill the view) calls `Room.loadNewer()`, except between a reset and the `showRequested` that follows it (`awaitingShow`), when the bottom shown is not one the user reached. A header (the bottom in this direction) holds the spinner `loadingNewer`. End while detached calls `Room.showLatest()`. The pill `roomJumpToLatest` is a button over the bottom of the list, shown by `Room.showJumpToLatest`; there is no shadow because the app has none elsewhere.
- **`MessageDelegate.qml`.** `found` gives `msgFound`: `Theme.ownTint` behind the message and a `Theme.own` bar `Theme.accentBarWidth` wide at its left. The thread pane's model answers `found` with `false`.
- **The search pane.** The picked row has `Theme.ownWash` (`messageSearchPicked`), "Opening…" beside the time (`messageSearchOpening`), and `messageSearchMissing` under the hint.
- **Testing knob.** `RC_HISTORY_PAGE_SIZE` (a positive whole number) sets `Tuning::page_size`, as `RC_THREADS_PAGE_SIZE` does for the thread list: the GUI tests make a room whose old messages are not loaded with a dozen posts.

## Thread replies

The room shows the parent, and the thread opens in the pane over the results; Back returns to the results. There is no "around" for threads, so the thread does not scroll to the reply. As built (3e):

- `rc_view::message_search_view::pick_target(message)` gives a `PickTarget { show, thread }`, kept in the row (`MessageRow.target`): a reply the room does not show (`shows_in_room`) shows its parent, one that was also sent to the room shows itself, and either opens the thread of its `tmid`; any other message shows itself and opens nothing. The core is unchanged: the frontend never asks it to show a hidden reply.
- `ThreadListState` has `search_held` (the core has a search) apart from `search_open` (the pane shows it). `pane` is `thread` while a thread is open, so a thread open with the search held is one opened from a result: opening a thread from the room still closes the search (`open_thread_steps`), while a result keeps it. `back_steps` / `escape_steps` from such a thread are `CloseThread` only (no thread list); `close_pane_steps` (the ×, and the threads button while the pane is open) closes thread and search; `open_search_steps` (Ctrl+F, the search button) closes the thread and shows the results as they were. `pick_steps` closes a thread left by an earlier pick when the new result is not a reply.
- `hub::show_result` runs `pick_steps`, `show_message(target.show)` and `open_thread(thread)`. The search model keeps the id of the picked row: a row is picked when it is that row and the room's `found` is its `target.show`, since a reply is shown by its parent.
- `RoomPage.qml` keeps `MessageSearchPane` (hidden, not destroyed, while `ThreadList.searchOpen` is false) so the rows, scroll and field survive; the field clears when `ThreadList.searchHeld` goes false. The thread's back button says "Results" while `searchHeld`.

## Steps

One PR each.

- **3a** (done): a refactor with no behaviour change in `rc_core`. `Fetch.older: bool` is `FetchKind`; the open room's saves go through `OpenRoom::persist`.
- **3b** (done): `rc_api` and the ports: `method_call`, `surrounding_messages`, `next_messages`, the adapter and the fake. wiremock tests in `rc_api/tests/rest.rs` (`result: false`, an error frame, a `401`); contract tests: the order, the edges, the flags, hidden replies, a deleted message giving `false`, a group, a direct message, `loadNextMessages` excluding the end, a group the user is not in.
- **3c** (done): the detached window in the core: unit tests in `timeline.rs` including a mirror following windows; `client/tests/jump.rs` (a held target makes no request; a second jump drops the first; live messages are dropped while detached and present after `show_latest`; `load_newer` joins; a missing or deleted message; reconnect, sending and another room; the store is never overwritten); an `rc_core` contract test: jump in a 15-message channel read four at a time (`start_with_page_size`), then `load_newer` until attached.
- **3d** (done): `rc_view` and the Qt side, with GUI tests: click and Enter show the old message with `msgFound` in view; the pane stays with the row picked; scrolling down reaches the latest; the pill; the not-found note.
- **3e** (done): thread replies: `pick_target`, the pane steps with `search_held`, `hub::show_result`, GUI tests in `message_search.rs`.

## Costs and risks

- One request of about 50 messages per jump to a message not held; the server uses the room and timestamp index.
- The window grows while scrolling and is not trimmed.
- Hidden thread replies use up the `limit`, so a window can be short: the view must ask for more while the content is shorter than the view.
- Inserting at row 0 of a BottomToTop list while detached may move the view (a GUI test covers it). Centring is imprecise until images load.
- The consistency of the window and the stored copy is the main correctness risk.
