# Threading

- **GUI thread**: runs the Qt event loop and owns every QObject and model. Nothing on it blocks, and it never waits on the network.
- **Tokio runtime** (multi-threaded, few workers), owned by `rc_core`:
  - **Core task**: owns what the accounts share (connector, file cache, store worker handle) and one session actor per account. It takes the `Client`'s commands one at a time and routes each to its account's actor. See [Accounts](accounts.md).
  - **Session actor**: one task per account, owning that account's authoritative client state (session, room list, message store and the open room's timeline), so the state needs no mutexes. It processes commands one at a time. Each history fetch carries an attempt id, and its answer is dropped if the room was closed or another fetch began meanwhile.
  - **Store worker**: shared by the core, not owned by the session actor. It runs the secret-store calls (keyring or memory), which block and may wait for the user to unlock the keyring. It takes them in order, one at a time, on blocking threads, so a save and a later clear never swap and the async threads never stall.
  - **I/O tasks**: the DDP connection (read loop, ping), REST requests and avatar/file downloads. They report back to the actor through channels, tagged with the login attempt (or fetch) they belong to, and the actor drops what is stale. The sync engine is the actor plus one such task per connection, which opens the realtime connection (`ServerApi::realtime`, a `Realtime`: a receiver of pushed events that closes the connection when dropped, and a sender through which the actor tells it which room is open) and forwards what it pushes. It works in cycles, one per connection: open the connection, fetch the rooms, and if a room is open fetch its newest page and the changes since the room was last up to date (see [Edits, deletions and reactions](edits-deletions-reactions.md)). The connection opens before the rooms are fetched, and what arrives until the list is set waits in a backlog and is replayed on top of it, so nothing between the snapshot and the subscription is lost. Subscription changes upsert or remove rooms; a pushed message joins the open room's timeline, and is ignored for any other room. A cycle ends when the connection ends or fails to open, or when its rooms fetch fails (an expired token ends the session instead): the actor drops the connection and starts a timer task that waits (`Backoff`: 1 s doubling to 60 s, cut randomly to between half and all of it, forgotten only when a cycle that opened the connection and listed the rooms then stayed connected for a minute, so a server that accepts and drops at once is not hammered), then starts the next cycle. The frontend is told with `Event::Connection` (`Waiting` with the wait, `Reconnecting` while a cycle tries, `Connected` once the rooms are listed again). `rc_qt` turns the latest one into the `Session.connectionText` property, which the banner of the room page shows. Reports and timers carry the cycle number, and logout, expiry and stopping abort the timer, so a stale one does nothing. Only the first listing of a session resets the room list; later ones are merged with `RoomList::sync` into inserts, updates, moves and removals, and a room that is gone is closed if it was open. The open room's newest page is merged by the timeline: it is appended if it touches the messages held, and replaces them if more than a page was missed.
- **Commands (GUI → core)**: sent on a non-blocking `mpsc` channel to the core task, which forwards them to the account's actor.
- **Events (core → GUI)**: the frontend gives `Client` an event callback, which the actors call from runtime threads, each in order for its own account, with the account's id. Events of different accounts may interleave. `Added` is an account's first event and `Removed` its last. In `rc_qt` the callback belongs to a hub (`hub.rs`), the one owner of the `Client` in the process, which keeps one cache per account (the latest session state and a mirror of the room list and of the open room's messages) and updates the cache of the event's account. It hands each event of the current account to every registered view model through `CxxQtThread::queue`, where the view model applies it as a diff (insert, update, move or remove rows). A view model registers when it is created, on the GUI thread, and replays the current account's cache under the same lock that queueing uses, so it misses nothing and applies nothing twice whenever QML creates it. Neither side waits for the other. Qt objects are never touched from a Tokio thread.
- **Shutdown**: dropping `Client` ends the core task, which drops every actor's command sender and waits for all the actors, which stop side by side: each ends its tasks and waits for its pending token revocations. Then the core drops its last handle on the store worker and waits for it to empty its queue, which includes the store clear of a logout. Both waits end at one deadline, 2 s after the actors began stopping, and the worker keeps running during the first, so 2 s is the most the GUI thread blocks, however many accounts there are.
