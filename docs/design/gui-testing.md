# GUI testing contract

There is one GUI test suite, `rc_gui_tests`, and it runs unchanged against both frontends. It is a Spix XML-RPC client and never links to either GUI. Each frontend embeds a server that speaks the same protocol:

- **QML frontend:** C++ Spix (`Spix::QtQuick`), started by the C++ host.
- **Slint frontend:** a Rust implementation of the Spix RPC server built on Slint's Rust testing API (`ElementHandle`, `query_descendants()`). The C++ `Spix::Slint` backend can't be used there: it needs C++-generated Slint components, and a Rust Slint app has a different Slint runtime.

Paths are kept shallow and decoupled from layout: `<window>/<name>`, where `name` is unique per window (for example `mainWindow/loginServerField`). A list row is addressed by its room id, not by its text (Spix's `"text"` selector), because room names aren't unique: the row's name is `room_<id>` and its parts (`roomName`, `roomKind_<kind>` (an icon, named after the room kind: `channel`, `private` or `direct`), `roomAvatar` (visible once the avatar image has loaded; its `text` is the `file://` URL), `roomAvatarPlaceholder` (the initials, visible until then), `roomUnread`, `roomMentions`) sit below it, as in `mainWindow/room_<id>/roomUnread`. The rail of servers is `serverRail`, with `addServerButton` (hidden while a new account waits for its login) and one tile per account, `serverTile_<index>`, `index` counting from 0 in the order the accounts were added. Tiles are addressed by position because neither a host nor a username is unique (two users on one server, or two addresses of one server, are two accounts) and the account ids are the app's own. A tile is a button: its `checked` says it is the account on screen. Its parts are `serverTileMonogram` (its `text` is the letter, hidden for a new account, which shows a plus), `serverTileMentions` (its `text` is the count, visible only above zero), `serverTileUnread` and `serverTileCurrent` (the short and the tall pip), `serverTileExpired` (the warning dot) and `serverTileBusy` (the ring), as in `mainWindow/serverTile_0/serverTileMentions`; `serverTileTip` is the tool tip beside the rail, visible while one is due. The login page has `loginTitle`, `loginLede`, `loginNotice`, `loginCancelButton` and `loginRemoveServerButton` besides its fields, and the sidebar `serverName` and `serverUser`. A message row is `msg_<message id>`, addressed like a room row, with `msgAuthor`, `msgAvatar` and `msgAvatarPlaceholder` (as for rooms), `msgTime`, `msgBody` (its `text` is the message as written), `msgBodyHtml` (its `text` is what is shown, as HTML), `msgMentionsMe` (visible if the message mentions the user) (or `msgSystem` for a system message, which has no author or body) and `msgDaySeparator` when the message starts a day, as in `mainWindow/msg_<id>/msgBody`; `msgEdited` (visible if the message was edited), `msgReactions` (visible if it has reactions) with a chip `reaction<N>` below the message for each one (N from 0, in the server's order, its `checked` says whether the user reacted) holding `reactionEmoji` (its `text` is the Unicode character, else the custom emoji's image address, else the shortcode) and `reactionCount`; the files of a message are `attachment<N>` below it (N from 0), with `attachmentImage` (visible once the picture has loaded; its `text` is the `file://` URL), `attachmentPlaceholder` (until then), `attachmentLink` for a file that isn't an image (its `text` is the address it opens) with `attachmentTitle` and `attachmentSize` in it, and `attachmentDescription`, as in `mainWindow/msg_<id>/attachment0/attachmentImage`; a message that quotes others has `quote<N>` above its text (N from 0, in order) with `quoteAuthor` (the username), `quoteTime`, `quoteBody` (its `text` is the quoted message as written, without the links of what it quotes itself) and `quoteBodyHtml` (as shown), as in `mainWindow/msg_<id>/quote0/quoteBody`; `msgBody` is hidden for a message of only files or quotes; the menu button `msgMenuButton` opens a menu whose items `msgQuoteAction`, `msgReactAction`, `msgEditAction` and `msgDeleteAction` are popups addressed from the window, and exist only while it is open; `reactionAdd`, the "+" after the chips, is visible when the message has reactions and can be reacted to; it and `msgReactAction` open the emoji picker, a popup of `emojiSearch` (the search box, focused, its `text` is the query) and `emojiGrid`, whose emoji are `emojiPick_<shortcode without colons>` (for `:tada:`, `emojiPick_tada`), addressed from the window and existing only while the picker is open and the grid shows them; clicking a chip toggles the user's own reaction; the room list has two sections, favorites first, `roomSection_favorites` and `roomSection_rooms`, each with a heading `roomSectionHeader` (its `text` is "Favorites" or "Rooms"), visible only while the user has favorites (the sections themselves always exist, with no height without favorites, so look at the heading for visibility and at the section's geometry for where it is); a right-click on a row opens its menu, whose items `roomFavoriteAction` (its `text` is "Add to favorites" or "Remove from favorites"), `roomMarkReadAction` (visible for a room that shows unread) and `roomMarkUnreadAction` (visible for one that shows read, except the open room) and `roomLeaveAction` (hidden for direct messages) are popups addressed from the window, as is the confirmation to leave, `roomLeaveDialog` (its `text` names the room) with `roomLeaveConfirm` and `roomLeaveCancel`; the search field above it is `roomSearchField` (its `text` is the query; Enter opens the result under the cursor, Escape clears it, and Ctrl+K focuses it) with `roomSearchClear` (visible while it holds text) and `roomSearchHint` (the "Ctrl K" keycap, visible while it is empty and unfocused), and `noNewsToast` above it (its `text` is "No new notifications"; visible for 2.5 s after F5 found no held channel news on any account), and while it holds something `roomSearchResults` (its `count` is how many rooms match) is visible and `roomList` is not: its rows are `searchResult_<id>`, with the parts of a room row (`mainWindow/searchResult_<id>/roomName`), because `room_<id>` is the room list's, and `roomSearchEmpty` is visible when nothing matches (its `text` is `No rooms, people or channels match “<query>”`, the query trimmed; it is visible only once the directory has answered, while `roomSearchResults` counts the rows of its own meanwhile). The results also have the server's directory in groups, with the labels `directoryGroup_channels`, `directoryGroup_people` and `directoryGroup_rooms` ("Channels", "People", "Your rooms", as their `text`), a row `directoryPerson_<username>` for a person and `directoryChannel_<room id>` for a channel with the parts `directoryName`, `directoryUsername` (a person whose name is another), `directoryHint` ("Message" or "View", visible while the pointer or the cursor is on the row), `directoryMembers` ("N members" of a channel, in the hint's place) and `directoryBusy` ("Opening…", while its action is under way), as in `mainWindow/directoryPerson_<username>/directoryHint`, `directoryMore_people` and `directoryMore_channels` ("N more, keep typing"), `directorySearching` (visible until the directory has answered), and `directoryError` (its `text` says why it could not be searched) with `directoryRetry`; and while the open room is a channel previewed without being in it, `roomComposer/composerJoin` ("Join", or "Joining…" and disabled) is visible in place of `composerSend`; `roomListError` under the room list, with `roomListErrorText` and `roomListErrorDismiss`, shows why the last command on a room failed; an unsent message also has `msgPending`, or `msgFailed` and `msgRetry`, which exist only in that state, so that a test, which can't know the id the client picked, finds the one unsent message by name alone (`mainWindow/msgFailed`); the room's composer is `roomComposer`, and its parts are found through it, since the thread pane has a composer of its own with parts of the same names (`roomComposer/composerField`; Enter sends, Shift+Enter starts a line; `roomComposer/composerSend`), with `composerEditBar` and `composerEditCancel` while a message is edited and `composerQuoteBar` with `composerQuoteAuthor`, `composerQuoteText` and `composerQuoteCancel` while one is quoted; the list is `messageList` (its `count` is the loaded messages, not those in view), with `historyStart` above the first message once nothing older exists. The Slint app also has `messageListOffset` (and `threadMessageListOffset`), an element that draws nothing and says in its `text` how far the list is scrolled up, in logical pixels; tests read it through `Gui::scroll_offset`, which reads `contentY` in the Qt app instead. The thread pane `threadPane` (visible only while it shows a thread or the room's threads; `roomThreadsButton` in the room's header toggles it, with `roomThreadsBadge` (visible while threads have replies the user hasn't read; its `text` is `unread` or, red, `mention`) and `roomThreadsBadgeCount` (its `text` is how many)) has, for a thread, `threadBackButton` and `threadTitle`, and in both cases `threadClose` (which closes both), and `threadMessageList` (its `count` is the loaded rows: the parent, then the replies), `threadReplies` (its `text` is "N replies", under the parent), `threadLoading`, `threadError` and `threadComposer`, a composer whose parts keep their names and are found through it (`threadComposer/composerField`, `threadComposer/composerSend`, `threadComposer/composerQuoteBar`, `threadComposer/composerEditBar`) and which has `composerAlsoToChannel` (its `checked` is whether the reply goes to the room too). The parent and the replies sent to the room are in both lists under the same `msg_<id>` names, and the room's rows come first in the tree, so the pane's are addressed through it: `mainWindow/threadPane/msg_<id>/msgBody`. A message of the room has `msgThreadSummary` under it once it has replies, with `msgThreadCount` ("N replies") and `msgThreadLastReply` ("Last reply" and the time, or the day), `msgThreadOpen` while its thread is the open one, and `msgInThread` (its `text` is "Replied in a thread" and the start of the parent's text) above a reply that was also sent to the room; the menu's `msgThreadAction` starts or opens the thread. None of these three is in the pane. The list of threads is `threadList` (it takes Escape, which closes the list; it stays, hidden, under a thread) with `threadListTitle` in the header, the segments `threadListFilterAll`, `threadListFilterFollowing` and `threadListFilterUnread` (their `checked` says which is on; the last has `threadListFilterUnreadCount` after its label, visible while there are unread threads), `threadListView` (its `count` is the loaded rows), `threadListLoading`, `threadListLoadingMore`, `threadListError` with `threadListRetry`, and `threadListEmpty` with `threadListEmptyTitle` and `threadListEmptyHint` once it has loaded with nothing in it. A row is `threadListRow_<parent id>`, with `threadListAuthor`, `threadListTime`, `threadListText`, `threadListSummary`, `threadListNew` (visible while the thread has replies the user hasn't read), `threadListMention` (visible while one mentions the user) and the avatar parts `threadListAvatar`, `threadListAvatarPlaceholder` and `threadListAvatarInitials`, as in `mainWindow/threadListRow_<id>/threadListSummary`; clicking the row opens the thread. The tests scroll with Home or with the wheel. Spix searches depth-first, so the path doesn't have to name the `ListView` or the delegate's other ancestors; it finds only rows that exist, and a `ListView` creates the delegates in view, so a test of a list longer than the window has to scroll first. In QML the name is the `objectName`; in Slint it is the `accessible-id`. Both composers (`roomComposer`, `threadComposer`) have the paperclip `composerAttach` (hidden while a message is edited or the room is previewed), the bar `composerAttachments` (visible while files wait for Send) with a chip `composerAttachment<N>` per file (N from 0, in the order attached) holding `composerAttachmentName` and `composerAttachmentSize` (their `text`), and its cross `composerAttachmentRemove<N>`; and the bar `composerUploads` (visible while uploads of the room, or of the open thread, are listed) with a row `upload<N>` per upload (N from 0, in the order asked) holding `uploadName`, `uploadStatus` (its `text` is `1.8 of 4.2 MB`, `Waiting · 4.2 MB`, `Posting…` or the reason it failed) and `uploadProgress` (hidden for a failed one), and the buttons `uploadCancel<N>` (a cross; "Remove" for a failed upload; absent while the message is posted) and `uploadRetry<N>` (failed only), as in `mainWindow/roomComposer/upload0/uploadStatus`. Spix cannot open a file dialog or drag files, so the paperclip takes the paths of the environment variable `RC_TEST_ATTACH_FILES` (separated as `PATH` is) when it is set, in place of the dialog, in builds with the cargo feature `test-attach-files` only (CMake turns it on with `ROCKETCHATQML_SPIX`, as it does `test-file-store`; a user's build never reads the variable): a test chooses its files with `common::launch_attaching`. A chip of an image file has `thumbnailImage` (visible only for a picture) besides its name and size. Ctrl+V in a composer's field attaches what the clipboard holds (ACT-012); a test can't copy, so builds with `test-attach-files` put `RC_TEST_CLIPBOARD_FILES` (paths, separated as `PATH` is), `RC_TEST_CLIPBOARD_TEXT` and `RC_TEST_CLIPBOARD_IMAGE` (a PNG file) on the clipboard when they start: `common::launch_pasting`. The Qt app only. The drop overlay (`dropOverlay`, `dropTitle` in the `DropZone` over the room and over the thread; in the Slint app over the room only) shows only while files are dragged and is not tested. In the Slint app the two bars are always made and have no height while empty, so `composerAttachments` and `composerUploads` are found only while visible, as in Qt. The GitHub page (Qt app only for now; the tests need no Rocket.Chat server but the app pointed at an `rc_test_github` stub with `RC_GITHUB_API`, and `RC_GH_PROGRAM` at a script that prints a token) has its tile `githubTile` at the bottom of the rail (a button: its `checked` says the page is on screen) with `githubTileFailing` (its `text` is the count of failing pull requests; visible only when connected and above zero), `githubTilePip` and `githubTileCurrent`, and a right-click menu whose item `githubDisconnectAction` is a popup addressed from the window, opened only while connected. The connect page has `githubConnectTitle`, `githubConnectGh` ("Use it"), `githubConnectTokenField` (its `text` is the token), `githubConnectToken`, `githubConnectBusy` and `githubConnectError` (its `text` is why it failed; visible only then). Once connected the sidebar has `githubTitle`, `githubStatus` ("<login>, updated 40 s ago", "updating…" or the error), `githubRefreshButton`, the tabs `githubTabMine` and `githubTabWatched` (their `checked` says which list shows) with `githubTabMineCount` and `githubTabWatchedCount` inside them, the list `githubPrList` (its `count` is the rows, the heading of the drafts included), `githubEmpty` (visible while it has none), the heading `githubDrafts` (its `checked` says the drafts show) with `githubDraftsTitle` ("Drafts 4"), and a row `prRow<index>` per row of the list (a button whose `checked` says its pull request is open; the heading counts as a row, so the first draft of two ready pull requests is `prRow3`, and only while the drafts show) with `prGlyph` (its `text` is `draft`, `failed`, `waiting`, `running`, `passed` or `none`), `prRepo` ("repo" or "repo, author" on Watched), `prAge`, `prBell` (visible when the user asked to be told when the CI ends), `prTitle` (styled text: the title, then the number) and `prBar` (visible when there are jobs) holding `prSegment<i>` (its `text` is `failed`, `running`, `cancelled`, `passed` or `waiting`), as in `mainWindow/prRow0/prBar/prSegment0`. The runners at the foot are `githubRunner<index>` with `githubRunnerName`, `githubRunnerStatus` and `githubRunnerLamp`. The main area has `githubPickHint` while no pull request is open, and for the one that is `prPageRepo`, `prPageNumber`, `prPageUpdated`, `prPageTitle`, `prPageHead`, `prPageBase`, `prPageReview`, `prPageBaseNote`, `prPageDraft` and `prPageOpenButton`, by their `text`. Under the header: the banner `prApproval` (visible only while runs wait for approval) with `prApprovalText` and the button `prApprove`; the actions `prMerge` (its `enabled` follows the view), `prMergeReason` (its `text`, visible only while Merge is disabled), `prMergeAnyway`, `prUpdateBranch`, `prRerunFailed` and `prNotify` (its `text` is "Notify me when done" or "Notifying you"), each visible only when it applies; the question of Merge, in place of those, `prConfirm` (its `text`) with `prConfirmMerge` or `prConfirmMergeAnyway` and `prConfirmCancel`; `prError` (why the last command failed, its `text`, visible only then) with `prErrorDismiss`; and `prToast` (its `text`, visible for a moment after a command is done). The checks are `prChecks` (the list that scrolls) with `prChecksHeading` and `prTally` (their `text`: "Checks failed", "1 failed, 2 running"), the bar `prChecksBar` whose segment `i` is `prChecksBar/prSegment<i>` (its `text` as in the rows' bars), a heading `prJobGroup<Failed|Running|Cancelled|Passed>` per group (a button whose `checked` says it is open, with `prJobGroupTitle`, "Failed 2", below it) and a row `prJob<index>` per job of an open group, `index` being the job's segment in the bar, with `prJobState` (`failed`, `running`, `cancelled` or `passed`), `prJobWorkflow` ("CI / "), `prJobName` and `prJobDuration` by their `text`, and the buttons `prJobRerun<index>` (visible for failed jobs with an id) and `prJobLog<index>` (visible with a URL). Spix can't move the pointer, so the lighting of a segment and its row under the pointer isn't tested. The path constants live in `rc_gui_tests`, which is the single source of truth.

Tests use only the part of the Spix protocol that both servers implement: clicks, the mouse wheel (`Gui::mouse_wheel`: Qt angle deltas, 120 per notch and positive up; the view glides on after the last step, so tests wait for what they expect), the mouse drag (`Gui::mouse_drag`: press, `steps` equal moves along a line, a hold, release, all played inside the app; points are logical px from the element's top-left; the Slint app answers after the release and the Qt app once the gesture is queued, so tests wait for what they expect; a Slint list flicks on unless the hold is longer than 100 ms; to drag the message list by its content press in the gutter left of the avatars, `main_window::MESSAGE_LIST_DRAG_X` from the list's left edge, where no message part selects, clicks or hovers in either app; the Qt app's list loses the first two moves of a drag to recognising it and the Slint app's nothing), key and text input, `existsAndVisible`, get/set of `text`, `checked`, `enabled`, `count` and geometry, `takeScreenshot` (a PNG of one element, cropped from the window; both servers write the file before they answer, and `Gui::screenshot` returns its bytes, so a test reads pixels at fractions of the image and needs no bounding-box arithmetic), `wait` and `quit`, the window's `frameCount` (`Gui::frame_count`: the frames it has drawn, counted from the first read, which returns 0, so callers use the difference of two reads; the Qt app counts `QQuickWindow::frameSwapped`, the Slint app `RenderingState::AfterRendering` through the window's rendering notifier, which the Spix server then holds; it is `None` where Slint's renderer has no notifier, as on the testing backend the GUI tests run on) and the scroll position of the message list (`Gui::scroll_offset`: logical pixels scrolled up from the newest message, 0 at the bottom and positive towards older messages, unchanged by older messages loading above the view; the Qt app's `ListView` gives it through `contentY`, and the Slint app, whose testing API can't read a flickable's position, through the `text` of the invisible element `messageListOffset` (`threadMessageListOffset` in the thread pane), which says it and is found wherever the list is scrolled), plus `getErrors`, which the `Gui` client checks after every call so that a wrong path fails the test. The core works asynchronously, so tests never sleep: `Gui::wait_until` and its `wait_until_visible`, `wait_until_hidden` and `wait_until_text` poll with a timeout and name what they were waiting for. `App::quit_and_wait` calls `quit` and waits for the app to exit by itself, so that it stops its core (a pending logout or store write finishes) before a test starts it again.

The harness starts the binary named by `RC_GUI_TEST_APP` with `--spix-port <free port>`, `QT_QPA_PLATFORM=offscreen`, `XDG_CACHE_HOME` set to a directory of its own (empty at launch, removed with the app: `App::cache_dir`, so a test can look at the avatar files) and `RC_SECRET_STORE=memory` (the app starts the core at launch, and its default secret store is the OS keyring, which on a developer machine is the user's real wallet) and `RC_FATAL_QML_WARNINGS=1`: in Spix builds of the Qt app a QML warning of the engine (a binding loop, a `TypeError`, a failed assignment, at load or later) is then printed and ends the app at once, so the test fails at its next call with the warning in its output (`console.warn` of our own QML, Qt's other warnings and an image that fails to download don't count: the Qt app loads custom emoji by URL, so a test that cuts the connection can make one fail, while an image file that can't be opened still counts; the Slint app ignores the variable). A test can override these with `App::launch_with`, for example with `RC_SECRET_STORE=file:<path>` to keep the session between two runs. `App::launch_with_options(&LaunchOptions)` also picks the binary by path (no `env::set_var`, so one process can launch the Qt and the Slint app) and puts a wrapper command in front of it (`perf stat ... -- <app> --spix-port <port>`; env is inherited through the wrapper). `App`'s child is then the wrapper, so dropping the `App` asks the app to quit through Spix and waits up to 5 s for the wrapper to exit by itself before killing it, as the wrapper (`perf`) writes its output only then; a wrapper killed after that timeout may leave the app behind. There are no process groups, so Ctrl-C in the terminal still reaches the app. The GUI tests are `#[ignore]`d, so a plain `cargo test` skips them (it runs before the app is built in CI) and never reports them as passed. ctest runs them with `--ignored` and `RC_GUI_TEST_APP` set; without it they fail. The tests that log in create their own users and rooms on the test server through `rc_test_server`, so they also need `RC_TEST_SERVER_URL`.
