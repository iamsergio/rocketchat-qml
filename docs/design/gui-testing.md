# GUI testing contract

There is one GUI test suite, `rc_gui_tests`, and it runs unchanged against both frontends. It is a Spix XML-RPC client and never links to either GUI. Each frontend embeds a server that speaks the same protocol:

- **QML frontend:** C++ Spix (`Spix::QtQuick`), started by the C++ host.
- **Slint frontend:** a Rust implementation of the Spix RPC server built on Slint's Rust testing API (`ElementHandle`, `query_descendants()`). The C++ `Spix::Slint` backend can't be used there: it needs C++-generated Slint components, and a Rust Slint app has a different Slint runtime.

Paths are kept shallow and decoupled from layout: `<window>/<name>`, where `name` is unique per window (for example `mainWindow/loginServerField`). A list row is addressed by its room id, not by its text (Spix's `"text"` selector), because room names aren't unique: the row's name is `room_<id>` and its parts (`roomName`, `roomKind_<kind>` (an icon, named after the room kind: `channel`, `private` or `direct`), `roomAvatar` (visible once the avatar image has loaded; its `text` is the `file://` URL), `roomAvatarPlaceholder` (the initials, visible until then), `roomUnread`, `roomMentions`) sit below it, as in `mainWindow/room_<id>/roomUnread`. A message row is `msg_<message id>` the same way, with `msgAuthor`, `msgAvatar` and `msgAvatarPlaceholder` (as for rooms), `msgTime`, `msgBody` (its `text` is the message as written), `msgBodyHtml` (its `text` is what is shown, as HTML), `msgMentionsMe` (visible if the message mentions the user) (or `msgSystem` for a system message, which has no author or body) and `msgDaySeparator` when the message starts a day, as in `mainWindow/msg_<id>/msgBody`; `msgEdited` (visible if the message was edited), `msgReactions` (visible if it has reactions) with a chip `reaction<N>` below the message for each one (N from 0, in the server's order, its `checked` says whether the user reacted) holding `reactionEmoji` (its `text` is the Unicode character, else the custom emoji's image address, else the shortcode) and `reactionCount`; the files of a message are `attachment<N>` below it (N from 0), with `attachmentImage` (visible once the picture has loaded; its `text` is the `file://` URL), `attachmentPlaceholder` (until then), `attachmentLink` for a file that isn't an image (its `text` is the address it opens) with `attachmentTitle` and `attachmentSize` in it, and `attachmentDescription`, as in `mainWindow/msg_<id>/attachment0/attachmentImage`; a message that quotes others has `quote<N>` above its text (N from 0, in order) with `quoteAuthor` (the username), `quoteTime`, `quoteBody` (its `text` is the quoted message as written, without the links of what it quotes itself) and `quoteBodyHtml` (as shown), as in `mainWindow/msg_<id>/quote0/quoteBody`; `msgBody` is hidden for a message of only files or quotes; the menu button `msgMenuButton` opens a menu whose items `msgQuoteAction`, `msgReactAction`, `msgEditAction` and `msgDeleteAction` are popups addressed from the window, and exist only while it is open; `reactionAdd`, the "+" after the chips, is visible when the message has reactions and can be reacted to; it and `msgReactAction` open the emoji picker, a popup of `emojiSearch` (the search box, focused, its `text` is the query) and `emojiGrid`, whose emoji are `emojiPick_<shortcode without colons>` (for `:tada:`, `emojiPick_tada`), addressed from the window and existing only while the picker is open and the grid shows them; clicking a chip toggles the user's own reaction; the room list has two sections, favorites first, `roomSection_favorites` and `roomSection_rooms`, each with a heading `roomSectionHeader` (its `text` is "Favorites" or "Rooms"), visible only while the user has favorites (the sections themselves always exist, with no height without favorites, so look at the heading for visibility and at the section's geometry for where it is); a right-click on a row opens its menu, whose items `roomFavoriteAction` (its `text` is "Add to favorites" or "Remove from favorites"), `roomMarkReadAction` (visible for a room that shows unread) and `roomMarkUnreadAction` (visible for one that shows read, except the open room) and `roomLeaveAction` (hidden for direct messages) are popups addressed from the window, as is the confirmation to leave, `roomLeaveDialog` (its `text` names the room) with `roomLeaveConfirm` and `roomLeaveCancel`; `roomListError` under the room list, with `roomListErrorText` and `roomListErrorDismiss`, shows why the last command on a room failed; an unsent message also has `msgPending`, or `msgFailed` and `msgRetry`, which exist only in that state, so that a test, which can't know the id the client picked, finds the one unsent message by name alone (`mainWindow/msgFailed`); the composer is `composerField` (Enter sends, Shift+Enter starts a line) and `composerSend`, with `composerEditBar` and `composerEditCancel` while a message is edited and `composerQuoteBar` with `composerQuoteAuthor`, `composerQuoteText` and `composerQuoteCancel` while one is quoted; the list is `messageList` (its `count` is the loaded messages, not those in view), with `historyStart` above the first message once nothing older exists. The thread pane `threadPane` (visible only while a thread is open) has `threadTitle`, `threadClose`, `threadMessageList` (its `count` is the loaded rows: the parent, then the replies), `threadReplies` (its `text` is "N replies", under the parent), `threadLoading`, `threadError` and `threadComposer`, a composer whose parts keep their names and are found through it (`threadComposer/composerField`, `threadComposer/composerSend`, `threadComposer/composerQuoteBar`, `threadComposer/composerEditBar`) and which has `composerAlsoToChannel` (its `checked` is whether the reply goes to the room too). The parent and the replies sent to the room are in both lists under the same `msg_<id>` names, and the room's rows come first in the tree, so the pane's are addressed through it: `mainWindow/threadPane/msg_<id>/msgBody`. A message of the room has `msgThreadSummary` under it once it has replies, with `msgThreadCount` ("N replies") and `msgThreadLastReply` ("Last reply" and the time, or the day), `msgThreadOpen` while its thread is the open one, and `msgInThread` (its `text` is "Replied in a thread" and the start of the parent's text) above a reply that was also sent to the room; the menu's `msgThreadAction` starts or opens the thread. None of these three is in the pane. The tests scroll with Home, since Spix has no wheel. Spix searches depth-first, so the path doesn't have to name the `ListView` or the delegate's other ancestors; it finds only rows that exist, and a `ListView` creates the delegates in view, so a test of a list longer than the window has to scroll first. In QML the name is the `objectName`; in Slint it is the `accessible-id`. The path constants live in `rc_gui_tests`, which is the single source of truth.

Tests use only the part of the Spix protocol that both servers implement: clicks, key and text input, `existsAndVisible`, get/set of `text`, `checked`, `enabled`, `count` and geometry, `wait` and `quit`, plus `getErrors`, which the `Gui` client checks after every call so that a wrong path fails the test. The core works asynchronously, so tests never sleep: `Gui::wait_until` and its `wait_until_visible`, `wait_until_hidden` and `wait_until_text` poll with a timeout and name what they were waiting for. `App::quit_and_wait` calls `quit` and waits for the app to exit by itself, so that it stops its core (a pending logout or store write finishes) before a test starts it again.

The harness starts the binary named by `RC_GUI_TEST_APP` with `--spix-port <free port>`, `QT_QPA_PLATFORM=offscreen`, `XDG_CACHE_HOME` set to a directory of its own (empty at launch, removed with the app: `App::cache_dir`, so a test can look at the avatar files) and `RC_SECRET_STORE=memory` (the app starts the core at launch, and its default secret store is the OS keyring, which on a developer machine is the user's real wallet). A test can override these with `App::launch_with`, for example with `RC_SECRET_STORE=file:<path>` to keep the session between two runs. The GUI tests are `#[ignore]`d, so a plain `cargo test` skips them (it runs before the app is built in CI) and never reports them as passed. ctest runs them with `--ignored` and `RC_GUI_TEST_APP` set; without it they fail. The tests that log in create their own users and rooms on the test server through `rc_test_server`, so they also need `RC_TEST_SERVER_URL`.
