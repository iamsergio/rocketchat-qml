# Message search

Searching the messages of the open room on the server (MSG-008). This is the server call, the core, what `rc_view` decides and the Qt pane; jumping to a result in the room (step 3), the Slint pane (step 5) and the search across all rooms (MSG-009) come later (see PLAN.md).

## What the user gets

- A magnifier button in the room's header, left of the threads button, with the tool tip "Search messages (Ctrl+F)"; it is lit while the pane shows the search and toggles it. Ctrl+F in the room page opens the pane if it is closed and focuses its field with the text selected.
- The search takes the place of the threads in the pane beside the room: opening it closes the list of threads or the open thread, and opening the list or a thread closes it. The header says "Search" and "in #room", and has the close button. Esc in the field closes the pane.
- The field has a magnifier and a cross (while it holds text); under it a faint hint, "Whole words · from:user · has:url · on:dd/mm/yyyy", which reads "Searching…" with a small spinner while a search runs and rows are on show.
- The results are grouped by day (a label: "Today", "Yesterday" or the date as the room's separators say it), newest first. A row has the avatar, the author, the time, and the start of the text on up to three lines with the words of the query in bold in the colour of what is the user's (nothing marked for a `/regex/` query). A reply in a thread has the line "In a thread". A system message shows the text the room shows for it.
- The cursor row has a lighter background, and only it: Up and Down move the cursor (wrapping over the day labels, starting on the first result), and so does the pointer, as in the mention popup. Enter and a click put the cursor there and show the message in the room (see below). A strip under the list shows the keys.
- The list area says what is going on: with an empty field "Search #room", how to search and the filters that work (see "What the server does"); a spinner while the first search runs with no rows to show; "No messages with “query”" when there are none; the error and a Retry button when the first page failed; at the end of the list a spinner while the next page loads, or the error and a Retry button when it failed. Reaching the end asks for the next page.
- The previous rows stay while a new search runs. Another room keeps the pane open with an empty field and searches nothing; logging out or switching the account closes it.

## What the server does

The contract tests (`crates/rc_api/tests/contract.rs`, `crates/rc_core/tests/contract.rs`) record it. Checked on Rocket.Chat 8.0.

- `GET /api/v1/chat.search?roomId=<id>&searchText=<text>&count=<n>&offset=<n>` answers `{messages: [...], success}`, the messages as the room history sends them (so `rc_api` parses them with the same type), plus a `score` per message that `rc_api` drops. Without `roomId` it is a `400 invalid-params`; no setting of the server is needed when there is one.
- It is a full-text (Mongo `$text`) search: whole words, ignoring case, so `Bananas` finds `banana` and `Banana` (the server stems), but `alph` doesn't find `alpha`. More than one word finds the messages with any of them; `"two words"` in quotes finds the phrase, and `-word` leaves out the messages with it.  The operators are in the next list.
- Operators in the text, found by probing (the `*_search_understands_*`, `*_orders_*` and `*_filters_by_day_*` contract tests keep them). They are taken out of the words and the rest is searched as above; several are all required (`from:` twice is not a filter). Alone, each finds the messages it describes; with a word, those among the ones with the word:
  - `from:<username>`: the author, with the name's case ignored (`FROM:` works too); `from:me` is the user who searches. `from:@<username>` is not an operator: `@name` is searched as a word, so it finds the messages that mention the name. `mention:<username>` (with or without `@`) finds the messages that mention it; `mention:me` is not the user.
  - `has:url` and `has:link`: a link in the text. `has:star` and `is:starred`: starred by the user who searches. `is:pinned`. `has:location`. A name the server doesn't know (`has:pinned`, `has:locations`, `IS:PINNED`, `foo:bar`) is searched as a word.
  - `before:`, `after:` and `on:` take a day as `day/month/year` (`30/10/2026`; `-` also separates, and the year may have two digits). `on:` is that day, `before:` and `after:` leave it out (`before:30/10/2026` is up to the 29th). The day is in the server's time zone, UTC on the test server (the tests cannot set a message's time, so cannot prove more). A date year first (`2026-10-30`), `today` and the like are no date: they are searched as words, so alone they find nothing. Alone they find every message of the days, system ones too.
  - `order:asc` puts the results oldest first (`order:desc` is the default) and pages by `offset` in that order; alone it finds nothing. The core never sends it: see below.
- `/regex/i` works, and then it is a substring search (`/alph/i` finds `alpha`); `/^alpha/i` finds the messages that begin with it. Such a result has no `score`. An invalid expression is a `400` whose message says "Regular expression is invalid".
- The order is by `ts`, newest first, whatever the score (a message with the word three times does not come before a newer one with it once). `count` and `offset` page through that order; an `offset` beyond the end gives an empty list.
- Thread replies are in the results, with their `tmid`, whether or not they were also sent to the room, and so are system messages (a topic change whose new topic matches comes as `room_changed_topic`).
- A direct message is searched like a room. A public channel the user is not in can be searched; a private group the user is not in is a `400` with no message, and so is a room that doesn't exist.
- An empty `searchText` is a `400` (`error-searchText-param-not-provided`); one of blanks only is a `200` with nothing.

## Searching

`AccountHandle::search_messages(room, query)` is called when the user changes the text; `more_message_search()` for the next page; `cancel_message_search()` when the panel closes. The core works as for the [member search](mentions.md#searching) (`crates/rc_core/src/account/message_search.rs`):

- the query is trimmed and loses its `order:` words (any case): the results are kept, paged and grouped newest first, so `order:asc zebra` searches `zebra` and `order:asc` alone is the empty query. What the frontend is told, and what the highlight and "No messages with …" use, is that cleaned query. It tells the frontend at once with `Event::MessageSearch(Some(MessageSearch { room, query, state: Searching }))`, and waits for the typing to stop (300 ms; `Tuning::message_search_debounce`, `RC_MESSAGE_SEARCH_DEBOUNCE_MS` in whole milliseconds, `0` for no wait: a testing aid) before it asks for `MESSAGES_PER_SEARCH + 1` (21) messages. The wait is a deadline of the actor, so it runs on the fake clock in tests;
- the answer is `Found { messages, more }` or `Failed(MessageSearchError)`: the first 20 of what came, in the server's order (newest first). `more` is the list's footer, a `More`: `Available` when the 21st was there, else `No`. The results are not filtered: replies the room doesn't show and system messages are in them, as the server finds them. `Failed` is for the first page only;
- `more_message_search()` works from `Available` and from `Failed(_)` (the retry): it tells `Found` with the same messages and `more: Loading` at once, and asks for the next 21 after the ones held. The answer tells `Found` with the 20 appended and `Available` or `No`; a failure tells the same messages with `more: Failed(..)`, so what the user reads stays (an expired token still expires the session). From `No` and `Loading`, with no search, and while the first page isn't here, it does nothing: `more` is the one record of whether a page is on its way;
- a newer search (another query or another room), a cancel and a logout end the request in flight, and the answer of one that was ended is dropped by its attempt id. An expired token expires the session. A cancel, and a logout that finds a search, tell `MessageSearch(None)`;
- the same room and query again does nothing, except after a `Failed`: then it asks again at once;
- an empty query asks nothing: it is told as `Found` with no messages and `more: No`, and ends the search in flight;
- the avatars of the authors found are wanted (`AvatarOwner::User`), as the member search's are, so the frontend needs nothing more than the `Event::Avatars` it follows already.

**A snapshot.** The results do not follow edits, deletions or reactions that happen after the answer, nor new messages: searching again brings them up to date.

## What `rc_view` keeps

`rc_view::Cache` keeps the last `MessageSearch` the core sent (`Cache::message_search`), `None` after a `MessageSearch(None)`, so that a view created late catches up. The pane being open is that: there is no other flag.

## What `rc_view` decides

`rc_view::message_search_view` is plain Rust (the time zone and the current time are parameters):

- `Results`, which the `Cache` keeps from `Event::MessageSearch` (`Cache::message_search_view`), holds the last `Found` while the next search runs, as `mention::Suggestions` does, and forgets it for another room, after `None` and after a failure (rows of another query would mislead). Its `view` gives a `View`: the `Status` (`empty`, `searching` when there are no rows to keep, `none`, `failed`, `results`), the rows, the `Footer` (`nothing`, `available`, `loading`, `failed` with the text; `nothing` while a search runs), the texts of the notes, the error, the hint under the field and whether a search is running over rows.
- `rows` gives a `Row::Day` label before the first message of each day (`message_view::first_of_day` and `day_label`) and a `Row::Message` per message: author, time (`time_text`), avatar owner, whether it is a reply in a thread, and the text, which is the message's body or the text the room shows for a system message (`system_text`), on one line and cut at 240 characters, escaped, with `<b>` around the whole words that are one of the query's words, ignoring case. The query's words are those of the query without the ones that start with `-` and not at all for a `/regex/`.
- `step_cursor` and `first_cursor` move the cursor over the message rows, wrapping; `stale_room` says that the search is of another room than the open one.
- The pane is a `Pane::Search` of `thread_list_view`: `ThreadListState` has `search_held` (the core has a search) and `search_open` (the pane shows it: `pane` is `search` unless a thread is open; a thread opened from a result hides the search, see [Jumping to a message](jump-to-message.md)); `pane_open` stays the list or a thread (the threads button). The commands are steps: `open_search_steps` closes the thread and the list first, `open_list_steps` and `open_thread_steps` close the search, `close_pane_steps` and `escape_steps` close it too (Back from a thread over the results returns to them), `toggle_search_steps` is the header button. Opening the search is `search_messages(room, "")`, answered at once as an empty `Found`, and closing it is `cancel_message_search()`.

## The Qt pane

- **Model:** `MessageSearch` (`rc_qt/src/message_search_model.rs`) is a list model and the view model of the pane. The hub tells it to show again on `Event::MessageSearch`, `TimelineStatus` (the search follows the open room: when it is of another one the model searches the new room for nothing and emits `fieldReset`, which empties the field), `Rooms` (the name) and when the account switches; switching the account cancels the search of the one left. It takes the `View` and announces the rows as an insert when they only add to the rows held (the next page, which keeps the scroll) and as a reset otherwise, moving the cursor to the first message; `Event::Avatars` announces the avatar role of the rows that show the new files. Text changes call `setQuery`, which searches the open room, `retry` and `retryMore` ask again, `reachedEnd` (QML calls it whenever the list's end is in view) asks for the next page only when the footer is `available` and there are rows. The pane's commands are `ThreadList`'s: `toggleSearch`, `openSearch`, `closePane`, `escape`, `searchOpen` and `searchHeld`.
- **QML:** `MessageSearchPane.qml` in `RoomPage` after the thread pane, `Theme.threadPaneWidth` wide, shown while `ThreadList.searchOpen`; `MessageSearchRow.qml` and `MessageSearchDay.qml` are the delegates of a `DelegateChooser` on `rowType`. The row's `checked` is the cursor (so that tests can read it); `picked`, the row chosen to be shown in the room, is a role that comes from the core's found message (`rc_view::message_search_view::pick_state`), and `opening` marks it while the room is still getting the message ("Opening…" beside the time); `MessageSearch.pick` puts the cursor on the row and calls `show_message`. `missingNote` is "This message no longer exists." while the core says the message picked is gone, until the next search or pick. The keycaps of the strip are `Keycap.qml`, which the mention popup uses too.

## Showing a result in the room

See [Jumping to a message](jump-to-message.md): `MessageSearch.pick` (a click, or Enter on the cursor's row) calls `show_message`; the pane stays open with the row picked.
